# Inline category creation from the dock has no confirmation step

**Folded into `.scratch/receipt-processing/issues/25-resolved-category-label-squeezes-the-line.md`
on 2026-08-29 — closed as absorbed, not rejected. The work described here is specified in that
ticket's agent brief. Do not implement from this file.**

Typing a category name that doesn't exist yet creates it inline on save, with no confirmation.
This risks creating an unintended category from a typo, and it's ambiguous in a specific way:
typing `Food - Milk` creates `Milk` as a subcategory of `Food` — probably what's wanted — but
there's no way to instead create a genuinely new top-level category literally named
`Food - Milk`. There's a workaround (create it explicitly via category management first), but the
inline flow doesn't make clear which outcome it's about to produce.

Request: a lightweight confirmation before an inline create commits, stating plainly what will be
created (name + parent, if any) so a typo or an ambiguous dash-separated name doesn't silently
create the wrong thing.

## Comments

Filed 2026-08-21 from the `potential-feature-ideas.md` idea list.

Triaged 2026-08-29 and folded into `receipt-processing/25`. The two tickets turned out to be the
same control at two different moments: category resolution runs through a single shared endpoint on
every picker in the app, and it creates the leaf at *resolve* time (on the field's `change` event),
not at commit. `25` was reporting the label that announces that creation *after the fact*; this
ticket asked for the notice *before*. Implementing either one alone would have meant rebuilding it
when the other landed.

Owner decisions taken there, both of which answer this ticket:

- **Propose, then confirm.** An unknown name no longer creates anything on resolve — it renders what
  *would* be created (child name + parent) with an explicit Create control, mirroring the
  Restore/Create-new pattern person resolution already uses for a soft-deleted match. That closes
  the typo risk this ticket was filed for.
- **The literal `Food - Milk` case is deliberately not solved.** `Parent - Child` keeps meaning
  *Child under Parent*; the confirm makes that reading visible, which was the actual complaint. A
  genuinely top-level category containing the separator is created from the Categories screen, which
  takes name and parent as separate fields. No escape syntax is introduced.

Closed as `wontfix` because that is this tracker's only closed state — it was **absorbed, not
rejected**, so it gets no `.out-of-scope/` entry, following the same carve-out the triage rules make
for an already-implemented request.
