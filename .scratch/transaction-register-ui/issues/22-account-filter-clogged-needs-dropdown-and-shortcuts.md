# The register account filter is a wall of checkboxes — replace with a compact control plus shortcuts

Status: resolved
Category: enhancement
Severity: medium
Blocked by: account-management/03 (re-parenting), which must ship first — see the Agent Brief
Area: Transaction register — filters (`register.html`, `RegisterController`/`RegisterService`/`RegisterFilter`)

## The problem

The account filter in the register is a flat `fieldset` of checkboxes: one per real account, then
one per per-person debt leaf (`register.html` lines 39–66). With several People, each holding
balances in more than one currency, every `Name (CUR)` leaf is its own checkbox, and the block
becomes a clogged wall that pushes the date/payee row and the register itself down the page.

The template already anticipates this — the People block carries a comment: *"The block grows bulky
with many people — collapsing it is a later UX pass."* This issue is that pass, widened to the whole
filter.

## What the owner wants

1. **A compact control instead of the inline checkbox wall.** Either a dropdown-with-checkboxes or
   an expandable panel that is collapsed by default and shows a summary of the current selection
   ("All accounts", "Cash", "3 accounts", …) when closed.
2. **Common single-account views should be fast.** The owner frequently wants *only one* account, or
   *only the non-people accounts* — both are tedious today (tick one / untick many).
3. **Bulk shortcuts.** At least "add People" / "remove People" (toggle every person leaf at once).
   Natural companions: "All", "None", and possibly "only this" affordance per row. Exact set is a
   design decision for triage.

## Constraints / notes for whoever picks this up

- **Server-rendered, htmx only** (§1.6) — the filter is a plain GET form (`method="get"
  action="/register"`). A dropdown-with-checkboxes that stays a normal multi-checkbox form under the
  hood is preferable to bespoke JS; if a small JS behaviour is unavoidable it must stay a leaf and
  not thread through the app.
- The filter value is `name="accountId"` repeated; a person leaf's value is its own account id, so
  People and real accounts are already homogeneous on the wire — shortcuts only need to know which
  ids are person leaves (`register.people()` vs `register.accounts()`).
- Selection must survive dock re-renders and the edit flow, which `hx-include` the active-filter
  hidden fields (`register.html` ~238, ~287) — keep the field name/shape or update those includes
  together.
- Check `docs/ui-transaction-register.md` §2.3 (filters) and §2.6 (People as filter options) for any
  ratified wording before changing behaviour; update the doc if the filter UX changes materially.

## Agent Brief

**Category:** enhancement
**Summary:** Replace the register's flat account checkbox wall with a five-tab picker strip whose
panel is htmx-swapped, and widen the register's read path to closed accounts.

**Current behavior:**

The register filter renders one `<fieldset>` containing a checkbox for every pickable open own
account followed by one for every per-person debt leaf — 66 checkboxes today, growing without
bound. It has no collapse, no summary, and no height cap, so it pushes the date/payee row and the
register itself down the page. Closed accounts are invisible to the register entirely: the account
set the register views is derived from open own accounts only, so a closed account cannot be
filtered *to*, not merely left unticked. The account list arrives in creation order (see
account-management/04).

`RegisterFilter` carries `accountIds` where an **empty list means "the default set"**, resolved
server-side to every open own account. The entry dock and split panel serialise the active filter
as repeated `viewAccountId` hidden fields and deliberately serialise **nothing** when the filter is
the default, so the server re-resolves it — carrying the resolved set would freeze the default and
drop accounts absent from the picker.

**Desired behavior:**

*The control.* The filter block becomes a one-line tab strip; the active tab is visually emphasised
(bold) and carries a count of accounts currently ticked, and inactive tabs carry no count:

> **Last used (19)** · Open · Persons · Closed · All

Clicking a tab htmx-swaps **only the panel below the strip** — it must not re-render the register or
run any ledger query. **Apply** is the sole action that re-renders the register. The panel is
collapsed on load and collapses again after Apply, leaving the strip as a one-line summary of what
is on screen. Switching tabs renders that picker's panel fresh with **all of its members ticked**;
ticks made in a previously open tab are discarded (the simplest behaviour — the owner explicitly
does not care which way this falls). Every panel offers **All** and **None** links.

*The five pickers.*

| Tab | Members |
|---|---|
| **Last used** | Open real accounts **and person leaves** having at least one posting inside the filter's active date range |
| **Open** | Open real accounts; person leaves excluded |
| **Persons** | Person leaves of **live** people only, people with any unsettled leaf ordered before fully settled people |
| **Closed** | Closed accounts |
| **All** | Every live own account — open, closed, and person leaves |

**Last used must include person leaves.** Excluding them would make transactions whose only own-leg
is a person's debt leaf produce no rows at all — 10 of the last 122 transactions — which is exactly
the regression reverted after owner testing on 2026-07-20 (plan stage 8b.1). Within the Last used
panel, person leaves sit in their own labelled group so a single group toggle clears them.

*"Last used" tracks the date filter.* Its membership is recomputed against whatever date range is
applied, not a fixed window.

*Selection encoding — reuse the existing idiom.* When **every** member of the active picker is
ticked, the form must submit **no `accountId` params at all**, so the server re-resolves the picker
against the submitted date range. A partial selection submits explicit ids, which are preserved
verbatim and intersected with the picker's membership. This yields the required date-change
semantics with no extra state: widening the range admits newly-qualifying accounts **only** if the
user was all-ticked; a partial selection is left alone; narrowing drops accounts that fall out.
Preserve the existing rule that an empty `accountIds` means "resolve the default", and keep the
entry dock's and split panel's refusal to serialise a defaulted account filter.

*Group ticking.* One generic client-side group-toggle mechanic, in a **new isolated JS leaf**
alongside the existing keyboard and image leaves (CLAUDE.md §1.6 — it must not thread through the
app), driven by markup so it is agnostic to where the grouping came from. It serves two different
groupings: account hierarchy (`parent_id`) and person ownership (the person↔account junction).
Person leaves are **not** hierarchy — they have no parent — so do not try to unify the two at the
data layer, only at the toggle. With JS disabled the panel must degrade to plain per-account
checkboxes that still work.

*Parent accounts are group toggles, never filter targets.* Posting is leaves-only, so a parent
account has no postings and no rows. Its checkbox is tri-state (all / some / none of its
descendants ticked) and its own id must **never** be submitted as an `accountId`, nor counted as a
picker member for the all-ticked encoding above. Render hierarchy depth using the existing
depth-annotated account query (the one the categories screen already uses), so indentation is
correct the moment parents exist.

*Closed accounts become viewable, never bookable.* Split the register's notion of own accounts into
a **read** set (all live own accounts, closed included) and a **post-to** set (open only). The
dock's Account picker, the transfer targets, and every other write-side picker keep using the
post-to set. This mirrors the view-vs-pick split that already excludes person leaves from pickers
while keeping them in the viewed set.

*Also delivered here:* the account ordering fix described in **account-management/04**. The account
list query the register filter reads orders top-level accounts by id (creation order); it must sort
alphabetically, parents before their children, alphabetical among siblings at each depth. Do not
implement 04 separately — it ships in this change.

**Key interfaces:**

- `RegisterFilter`: gains the active picker alongside `accountIds`. Preserve the "empty
  `accountIds` means the default set" contract exactly.
- `RegisterService`: the method resolving own accounts splits into a read set and a post-to set; a
  new resolver produces each picker's membership and the active picker's tick state.
- `RegisterView`: today it exposes `accounts()` and `people()` as two flat lists feeding one
  fieldset. It should instead expose the tab strip (name, active flag, ticked count for the active
  tab) and the active picker's panel model, including group structure and depth.
- `RegisterController`: accepts the active picker as a request param; gains an endpoint returning
  the panel fragment for a picker (htmx swap target). An inbound link carrying explicit
  `accountId`s with **no** picker param activates the **All** tab — this covers the landing page's
  pinned-account link and the People page's per-person link. The receipt `?selected=` jump keeps
  deriving its own filter and is otherwise unchanged.
- `PersonBalanceSummary` / the person read service: reuse for settled-vs-unsettled ordering and for
  a person's leaf-id set. A fully settled person already has an empty position list; the leaf-id set
  already backs the People page's register link. Do not write a new settled/unsettled query or
  introduce a new term for it.
- The depth-annotated account query returning account plus depth, already ordered alphabetically
  depth-first: reuse it for the hierarchy-rendering pickers.
- The plain live-accounts-by-type query: fix its ordering (account-management/04).
- The entry dock and split panel hidden active-filter fields: they must also carry the active
  picker, or a commit re-render loses the tab. Keep the field names and the repeated-`accountId`
  wire shape otherwise unchanged.

**Acceptance criteria:**

- [ ] The filter renders as a single-line tab strip: `Last used`, `Open`, `Persons`, `Closed`,
      `All`, with the active tab emphasised and showing a ticked count, and inactive tabs showing
      no count.
- [ ] The panel is collapsed on page load and after Apply.
- [ ] Clicking a tab swaps only the panel fragment; the register rows are not re-rendered and no
      register query runs.
- [ ] Pressing Apply is the only action that re-renders the register rows.
- [ ] `Last used` contains open real accounts *and* person leaves having a posting inside the
      applied date range; a transaction whose only own-account leg is a person's debt leaf still
      produces a row under the default view.
- [ ] `Open` excludes person leaves; `Persons` lists live people's leaves only, unsettled people
      first; `Closed` lists closed accounts; `All` contains open, closed, and person leaves.
- [ ] With every member of the active picker ticked, the submitted query string contains no
      `accountId` parameter; with a partial selection it contains one per ticked account.
- [ ] Widening the date range while all-ticked admits newly-qualifying accounts; widening while
      partially ticked leaves the selection unchanged; narrowing drops accounts that leave the
      picker.
- [ ] Ticking a parent account ticks all of its descendants and the parent's own id is absent from
      the submitted `accountId` values; the parent renders a partial state when only some
      descendants are ticked.
- [ ] Ticking a person's group ticks all of that person's currency leaves; a single leaf can still
      be ticked alone.
- [ ] With JavaScript disabled, every individual account checkbox still ticks and Apply still
      filters.
- [ ] A closed account can be selected and its rows and running balance render; the entry dock's
      Account picker and the transfer targets still offer open accounts only.
- [ ] A link carrying explicit `accountId`s and no picker opens on the `All` tab with exactly those
      accounts ticked; the landing page's pinned-account link and the People page's per-person link
      both still land correctly.
- [ ] The account list is ordered alphabetically, parents before children, alphabetical among
      siblings at each depth — on both the register filter and the accounts screen
      (account-management/04).
- [ ] Committing a transaction from the dock re-renders the register under the same active picker
      and selection.
- [ ] `docs/ui-transaction-register.md` §2.3 is rewritten: it currently documents the account
      default as "Current bank accounts + cash" while the code resolves every open own account, and
      **neither** will be true afterwards — the default becomes the `Last used` picker, all ticked.
- [ ] `CONTEXT.md` records the **open** (not closed) vs **live** (not soft-deleted) distinction.
- [ ] `./gradlew check` is green, with the picker membership queries covered in `sqlLogicTest`
      (activity-in-range and settled-ordering are aggregating, multi-table, SQL-resident), the panel
      fragment and Apply round trip covered as controller/htmx acceptance in `integrationTest`, and
      picker resolution plus the all-ticked encoding covered in the unit tier with repositories
      mocked.

**Out of scope:**

- **A "Cash" picker.** Considered and dropped during triage: `cash_account` is a receipt-detection
  flag meaning "the account a `Bar`/cash line resolves to in this currency", carried by 2 accounts.
  With hierarchy in use it becomes a one-click selection inside `Open` or `All`. Do not add the tab
  and do not repurpose the flag.
- **Reusing `show_on_main_page`** to seed the default account selection. It means "pinned to the
  landing page Balances panel" and stays that way.
- **Making closed accounts bookable**, or changing any write-side picker's membership.
- **Re-parenting accounts** — that is account-management/03 and ships first.
- **Date-range quick presets** — transaction-register-ui/12.
- **Column re-sorting** of the register, which remains deferred (plan §14).
- **Retiring the 36 dormant accounts.** That is the owner's data hygiene, deliberately not a
  precondition: the design must stay comfortable with a messy account table.

## Resolution (2026-09-07, owner-confirmed)

Shipped on branch `feat/register-filter-picker` (8 commits). The flat checkbox wall is now a
five-tab strip — `Last used · Open · Persons · Closed · All` — over a collapsed `<details>` panel:

- Tabs are `<a>` links that htmx-swap only the control (`GET /register/filter-panel/<picker>`),
  no ledger query; **Apply** is the only thing that re-renders the register.
- `RegisterPicker` on `RegisterFilter`; empty `accountIds` = "the whole picker", re-resolved
  server-side; an all-ticked selection collapses back to empty on the wire.
- Parent accounts and a three-level `Persons → person → currency` hierarchy are tri-state group
  toggles, driven by `filter-groups.js` (the sanctioned third JS leaf — CLAUDE.md §1.6 updated).
- Closed accounts: viewable via the Closed/All tabs (a "closed" marker on the row), never
  bookable — `RegisterService` split into a read set and a post-to set.
- account-management/04 (alphabetical depth-first ordering) rode along via the shared
  `LIVE_TREE_CTE`.
- Docs: `ui-transaction-register.md` §2.3 rewritten; `CONTEXT.md` gained an Accounts section.

Three rounds of owner testing fixed: tab clicks not switching (submit-button double-fire +
htmx query-string strip → `<a>` + path segment), person hierarchy too flat (→ 3 levels), Apply
ignoring the active tab (picker moved to a hidden field inside the swapped fragment).
