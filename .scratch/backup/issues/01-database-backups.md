# Database backups — `pg_dump` to file, on a button and on a schedule

Status: ready-for-agent
Category: enhancement
Severity: medium
Area: New feature — new `backup` module + its own page

> *This was generated by AI during triage.*

Filed 2026-08-23 as a rough capture ("in-cluster template backups"), grilled to a decided design on
2026-08-29. The original mechanism — `CREATE DATABASE … TEMPLATE hauptbuch` in the same cluster —
was **rejected during grilling**; see *Why not the template copy* below. The file was retitled to

## Why this is worth having

NFR-03 (documented PostgreSQL backup/restore, **Must**) is on the books and unbuilt; the plan parks
it under *Ops & hardening* as a runbook item. There is no runbook — `deploy/README.md` covers Java,
Postgres, systemd and receipt storage, and says nothing about backups. The owner wants to press a
button on the Pi rather than remember a shell incantation, and wants it to also happen on its own.

## Why not the template copy

Recorded so the idea is not re-proposed later:

- **The source database is never session-free.** `CREATE DATABASE … TEMPLATE src` requires zero
  other connections to `src`. The receipt batch poller is a `@Scheduled` job that takes a connection
  every 30 seconds unconditionally, even when idle. Quiescing the Hikari pool is not enough; the app
  actively reconnects twice a minute, forever.
- **The app's DB role cannot do it.** The deploy runbook creates the role without `CREATEDB`. Making
  this work would mean granting `CREATEDB` to the live runtime role.
- **It doesn't survive the failure the Pi actually has.** A copy in the same cluster on the same SD
  card dies with the card. A dump file is at least portable off the box.
- **It made retention urgent for no reason.** Each template copy clones the entire database; a
  `pg_dump -Fc` of the current ledger (166 transactions) is **0.07 MB**. A year of daily dumps is
  under 30 MB.

## Agent Brief

**Category:** enhancement

**Summary:** Add a `backup` module that writes `pg_dump` snapshots of the ledger database to disk —
on demand from a page, and daily on a schedule — with a listing, retention, download, and a
documented restore procedure.

**Current behavior:**
No backup capability exists anywhere. There is no `backup` module, no `pg_dump` invocation in the
codebase, and no backup section in the deployment runbook. NFR-03 is unmet.

**Desired behavior:**

A new top-level `backup` module (Modulith module per CLAUDE.md §1.1) owning its own page and
controller, linked from the Settings page. It provides:

1. **Take a backup now** — a button that runs `pg_dump` in PostgreSQL custom format (`-Fc`) against
   the configured datasource and writes the result to the backup directory. Reports success or
   failure to the user; a failure must be visible in the UI, not just logged.
2. **Daily automatic backup** — an in-app `@Scheduled` job at a fixed hour. `@EnableScheduling` is
   already enabled on the application class, and the receipt batch poller is the pattern to follow.
   If the app was not running at the scheduled hour, take the missed backup at startup (a Pi that
   reboots overnight must not silently skip a day).
3. **A listing** — every backup on disk, newest first, showing timestamp, size, and whether it was
   manual or automatic.
4. **Retention** — after each automatic backup, delete automatic backups beyond the newest N
   (default 30, configurable). **Manual backups are never swept automatically** and are removed only
   by an explicit per-row delete in the UI. Never delete the last remaining backup of any kind.
5. **Download** — a per-row download of the dump file.
6. **Restore instructions** — a per-row panel rendering the exact command sequence for that specific
   backup (stop the service, drop and recreate the database, `pg_restore`, start the service) with
   the filename already substituted, ready to copy.

**Key interfaces and shapes:**

- **The filesystem is the source of truth. Do not add a `backup` table or a Flyway migration.** A
  database table listing backups would itself be inside every dump, so restoring a month-old backup
  would also restore a month-old list of backups. The listing is a directory read.
- **Manual vs. automatic is encoded in the filename**, e.g.
  `hauptbuch-<yyyyMMdd>-<HHmmss>-manual.dump` / `-auto.dump`, so retention can classify from a
  directory listing alone.
- **Configuration** under a `hauptbuch.backup` property group: a storage root defaulting to
  `/var/lib/hauptbuch/backups` in the Pi config and a git-ignored local directory in dev (follow the
  existing receipt-storage property and its `.local-receipts/` gitignore convention), a retention
  count, and the scheduled hour.
- **A narrow seam for the external process** — a runner type whose single responsibility is invoking
  `pg_dump` and reporting the outcome. The service that orchestrates naming, scheduling, and
  retention must be testable with that runner mocked.
- **Database credentials go in the subprocess environment as `PGPASSWORD`, never in the command
  arguments** — argv is world-readable via `ps`. Connection host/port/database come from the
  configured Spring datasource, not a second copy of the settings.
- **The backup directory is created mode `0700`.** A dump contains the `settings` row, and therefore
  the Anthropic API key (NFR-04's sanctioned exception, data-model §3.8).

**Testing** (CLAUDE.md §6 — put each piece in the right tier):

- Unit tier: filename generation, the manual/automatic classification, and the retention selection
  logic (including "never delete the last one" and "never sweep a manual") with the process runner
  and filesystem mocked. This is where the real logic lives.
- Integration tier: one round-trip that runs the actual `pg_dump` binary against the Testcontainers
  Postgres and asserts a non-empty, restorable dump; plus the controller/htmx acceptance tests for
  the page. **Guard the binary test with an assumption so a machine without `pg_dump` on `PATH`
  skips rather than fails** — this is a new host dependency the build has never had. Note the client
  must be at least the server's major version.
- No `sqlLogicTest` work; this feature has no SQL-resident logic.

**Documentation:**

- Add a **Backup and restore** section to `deploy/README.md`: where dumps live, what the retention
  is, the full restore procedure, and the two stated limitations below.

**Acceptance criteria:**

- [ ] A `backup` module exists as a top-level package and `ApplicationModules.verify()` passes.
- [ ] Pressing the button produces a new `-manual.dump` file in the configured directory, and the
      new backup appears in the listing without a full page reload.
- [ ] A `pg_dump` failure (bad credentials, missing binary) surfaces as a visible error in the UI and
      logs at WARN or ERROR per the CLAUDE.md §5 level ladder; it does not leave a partial file
      behind in the listing.
- [ ] The scheduled job produces an `-auto.dump` file; if the app starts and no backup exists for the
      current day, a catch-up backup is taken at startup.
- [ ] After more than N automatic backups exist, the oldest automatic ones are deleted down to N.
- [ ] Manual backups are never deleted by retention, regardless of age or count.
- [ ] With exactly one backup remaining, retention deletes nothing.
- [ ] The listing shows timestamp, size, and manual/automatic for each backup, newest first.
- [ ] Download returns the dump file with a sensible filename and content type.
- [ ] The restore-instructions panel renders the actual filename of that row, not a placeholder.
- [ ] No new Flyway migration is added.
- [ ] `PGPASSWORD` does not appear in the process's command arguments.
- [ ] `deploy/README.md` has a Backup and restore section covering the restore procedure and the
      limitations.
- [ ] `./gradlew check` is fully green (CLAUDE.md §1.9).

**Out of scope:**

- **Receipt images.** Backups are database-only. Images stay on disk unmanaged by this feature; the
  runbook tells the operator to `rsync` the receipt storage directory separately.
- **Restore from the UI.** No restore button, no staged-restore-on-boot. A restore must drop and
  recreate the live database, which the app cannot do to its own open connection, and the systemd
  unit deliberately denies the app the privilege to stop and start itself. Restore is a documented
  manual procedure.
- **The in-cluster `TEMPLATE` copy**, and any `CREATEDB` grant to the app's role.
- **An every-N-transactions trigger.** It would couple `backup` to `ledger` to watch a counter, the
  threshold is arbitrary, and the manual button serves the "about to do something risky" case better.
- **Copying backups off the Pi** (scp/rsync to a NAS, cloud upload). Separate concern; the download
  button is the manual path for now.
- **FR-PROF-05 per-profile backups.** Profiles do not exist yet.
- **Encrypting the dump at rest.** Directory permissions are the control for now.

**Stated limitations — document these, do not try to solve them:**

- A restored ledger may reference receipt images that no longer exist on disk. Thumbnails self-heal
  at serve time, but the original-image read does not — viewing such a receipt will error.
- Backups land on the same SD card as the live database, so on their own they do not survive disk
  failure. Their value is recovering from mistakes, plus producing a portable file to carry off the
  Pi.
- Restoring an older dump into a newer app is a forward Flyway migration on start, not a rollback.

**Follow-up this does not close:** NFR-03 also asks for a one-click **data + attachments** export.
This feature delivers the documented backup/restore half only; the attachments-export half remains
in the *Ops & hardening* backlog.
