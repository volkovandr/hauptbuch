# Account list only shows one level of indentation — grandchildren look like children

Status: ready-for-agent
Category: bug
Severity: minor
Area: Account management (account list screen, hierarchy rendering)

The accounts list distinguishes a parent from its direct children visually, but a grandchild
renders at the same indent level as a child — there's no visual difference between depth 1 and
depth 2+ in the hierarchy.

Request: indent each additional level further (or otherwise visually distinguish depth beyond one
level) so the tree structure is legible at a glance.

## Agent Brief

**Category:** bug
**Summary:** The accounts list indents every non-top-level account by one fixed step, so a
grandchild is indistinguishable from a child. Render indentation from each account's true
hierarchy depth, matching the categories screen.

**Current behavior:**
The accounts screen groups assets and liabilities and marks any account with a parent as a child
with a single CSS class. The shared stylesheet computes the indent as
`calc(var(--depth, 1) * 1.75rem)`, but the accounts template never sets `--depth`, so it always
falls back to `1`. Result: child, grandchild, and any deeper account all sit at exactly one 1.75rem
indent — no visual difference between depth 1 and depth 2+.

The controller feeds the screen a flat `List<Account>` from the service's manageable-accounts read
(live asset + liability accounts, with per-person debt leaves filtered out), split into assets and
liabilities by type. That read carries no depth annotation.

**Desired behavior:**
Each row on the accounts list is indented in proportion to its depth in the parent chain (0 = top
level, 1 = child, 2 = grandchild, …) to arbitrary depth, so the tree is legible at a glance —
identical in mechanism to how the categories screen already renders its hierarchy.

- Accounts remain listed depth-first: every account immediately followed by its own descendants,
  and alphabetical among siblings.
- Assets and liabilities stay in their separate groups; grouping and every other column
  (swatch/hue, name link, `closed` tag, currency) are unchanged.
- Per-person debt leaves stay excluded from this screen, exactly as now.
- Closed accounts stay listed.
- Empty groups still show their "No … accounts yet." line.

**Key interfaces:**
- A depth-annotated read already exists for exactly this purpose: the repository's recursive
  parent-chain walk returning account + depth, its pass-through on `AccountService`, and the
  `AccountNode(account, depth)` record. The **categories** module already consumes this via a
  `manageableCategories()`-style service method that filters the auto-managed currency leaves out
  of the annotated stream; mirror that shape.
- Add an accounts-side equivalent of the existing flat manageable-accounts read that returns the
  depth-annotated nodes instead, preserving the same person-debt-leaf exclusion. Person debt
  leaves are always leaves (per-(person, currency) asset accounts), so filtering them from the
  depth-first list cannot orphan a descendant or disturb remaining depths.
- The accounts controller should hand the template `AccountNode`s (split into assets / liabilities
  by `account().type()`) rather than bare `Account`s.
- The template should set the depth the same way the categories template does: apply the child
  class when `depth > 0` and set the `--depth` custom property inline to the node's depth. No CSS
  change is expected — the shared rule is already written for a per-row `--depth`. Do not
  hand-format; run `spotlessApply`.

**Acceptance criteria:**
- [ ] On the accounts screen, a child indents one step, a grandchild two steps, a
      great-grandchild three, and so on — verifiable in the rendered HTML (the child class plus a
      `--depth` value matching the account's real depth).
- [ ] A top-level account has no indent and no child class.
- [ ] Assets and liabilities are still rendered as two separate labelled groups; within each,
      accounts appear depth-first with siblings alphabetical.
- [ ] Per-person debt leaves do not appear on the accounts screen.
- [ ] Closed accounts still appear, still tagged `closed`.
- [ ] An asset/liability group with no accounts still shows its "No … accounts yet." message.
- [ ] Integration coverage in the accounts screen test asserts the depth-driven indentation for
      an account nested at least two levels deep (seed a small parent → child → grandchild tree).
      Follow the existing categories screen integration test for the assertion style.
- [ ] The manageable-accounts service change is covered in the accounts service unit test
      (person-leaf exclusion preserved; depth annotation passed through) and the repository
      round-trip / SQL-logic coverage for the depth query already stands — do not duplicate it.
- [ ] `./gradlew check` is fully green (all three suites + `ApplicationModules.verify()` + every
      quality tool).

**Out of scope:**
- The register's account-filter ordering and any other consumer of the flat accounts read
  (tracked in issue 04).
- Showing account balances on this screen (issue 01).
- Reparenting / changing an account's parent (issue 03).
- Any change to the CSS indent step size or the hierarchy data model.
- Collapsing/expanding tree nodes or any interactive tree behaviour — this is static indentation
  only.
