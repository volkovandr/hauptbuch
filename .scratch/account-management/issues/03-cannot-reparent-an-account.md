# An account's parent cannot be changed after creation

Status: ready-for-agent
Category: enhancement
Severity: medium
Area: Account management (account editor, `AccountService`/`AccountsController`)

## The problem

A parent can be chosen when an account is **created** — the create form offers a Parent select and
`AccountDraft` carries `parentId` — but there is no way to change it afterwards. The account update
path takes name, hue, and the main-page flag only.

The consequence is that a book which was built flat can never grow a hierarchy. The owner's book has
41 own accounts, **all top level**: the only way to nest any of them today would be to recreate them,
which would orphan their postings.

## Agent Brief

**Category:** enhancement
**Summary:** Allow an existing account's parent to be changed (including to top level) from the
account editor, under the same validity rules that already govern a parent chosen at creation.

**Current behavior:**

`AccountDraft` carries a `parentId` and the create path validates it — the parent must be a
same-type account, and the invariant behind that check is that a parent must not itself hold
postings, since posting is leaves-only (data-model §5). The account update path accepts only name,
hue, and the main-page flag; there is no re-parent operation anywhere in the module, and the account
editor offers no Parent control.

**Desired behavior:**

The account editor lets the operator move an account to a different parent, or to top level. The
move is refused, with a message naming the reason, when it would break an invariant:

- The **new parent must be the same account type** as the account being moved — the rule the create
  path already enforces.
- The **new parent must not hold postings.** Moving a child under an account that already has
  postings would make that account a non-leaf while it has rows, violating leaves-only. An account
  with no postings may become a parent.
- The move must **not create a cycle** — an account cannot be moved under itself or under any of its
  own descendants. This is new: the create path cannot produce a cycle, so no existing check covers
  it, and it must walk the full parent chain rather than checking one level.
- **Auto-managed leaves must not be re-parented** — per-currency category leaves and per-person debt
  leaves belong to the machinery that provisions them, and moving one would detach it from its
  parent category or its owner.
- The **account being moved may hold postings.** It stays a leaf; only its position changes. This is
  the common case and must be allowed.

Moving an account carries its own children with it — the subtree moves as a unit, since only the
moved account's `parentId` changes.

**Key interfaces:**

- The account update operation: gains the ability to set a parent, including clearing it to make the
  account top level. Distinguish "parent not supplied" from "parent explicitly cleared" so an update
  that does not mention the parent leaves it alone.
- The existing usable-parent validation used by the create path: reuse it rather than writing a
  second set of rules, and extend it with the cycle check, which applies only to a move.
- The account editor template: a Parent control offering the same-type candidates plus a top-level
  option, defaulted to the account's current parent.

**Acceptance criteria:**

- [ ] An account with postings can be moved under a childless, postingless, same-type account, and
      its postings and running balance are unaffected.
- [ ] An account can be moved back to top level.
- [ ] Moving an account under a different-type account is refused with a message naming the reason.
- [ ] Moving an account under one that holds postings is refused with a message naming the reason.
- [ ] Moving an account under itself, or under any descendant at any depth, is refused — verified at
      grandchild depth or deeper, not just one level.
- [ ] A per-currency category leaf and a per-person debt leaf cannot be re-parented.
- [ ] Moving a parent moves its whole subtree; descendants keep their relative structure.
- [ ] An update that does not mention the parent leaves the existing parent unchanged.
- [ ] `./gradlew check` is green, with the validation rules covered in the unit tier (repositories
      mocked) and the update round-trip covered in `integrationTest`.

**Out of scope:**

- Merging or reassigning accounts — that is the `operations` module's territory.
- Re-parenting **categories** from the categories screen, which has its own subdivide/merge
  operations.
- Bulk or drag-and-drop re-parenting; one account at a time from the editor is enough.
- Any change to how a parent's balance is computed (it is already the sum of its descendants).

## Comments

### Implemented 2026-09-06 — awaiting owner confirmation

Branch `account-management/reparent`.

- New `AccountReparenter` (`accounts` module) owns the validated move: reuses the create path's
  `requireManageable` / `requireUsableParent` (widened to package-private), adds the move-only rules
  — per-person debt leaf can't be moved; new parent can't be a different type, hold postings, be
  closed, be an auto-managed leaf, or sit in the account's own subtree (cycle check via
  `findSubtreeAccountIds`, arbitrary depth). Its own class because `AccountService` is at the
  static-analysis class-size ceiling.
- `AccountRepository.updateParent` widened `long` → `Long` so it can clear to the top level.
- `AccountsController`: new `POST /accounts/{id}/parent`; a refused move flashes the reason and
  returns to the editor (page-level warning), a successful one returns to the list.
- `account-edit.html`: new "Structure › Parent" section (same-type candidates + "top level",
  current parent pre-selected), shown only for a managed non-person-leaf account.
- Tests: `AccountReparenterTest` (11 unit), `AccountRepositoryIntegrationTest` (null-clear,
  whole-subtree move), `AccountsScreenIntegrationTest` (offer control, pre-select, hide for person
  leaf, move + back to top, refused-with-reason). `./gradlew check` green.
- Reviewed via `/code-review`: hardened the new-parent checks (person/currency leaf, closed) and
  moved the error banner to page level so a refused move on a hidden-section account still shows.
