# A category can't be deleted when every other category of its type has currency leaves

Status: ready-for-agent
Category: bug
Severity: high
Area: Category management — `CategoryService.deleteTargetOptions`, `operations.DeletionService`,
`operations.CurrencyLeafService`, `PostingReassignmentRepository`, `category-edit.html` delete panel

> Split during triage on 2026-08-22. This ticket originally carried two independent defects; the
> other one — *deleting an empty category still demands a reassignment target* — is now
> `category-management/06`, which is `ready-for-agent`. This ticket keeps the target-eligibility
> defect, which needs a domain decision first.

## Request (owner)

Created a new income category, then tried to delete it right away to check the new logging. The
system refuses: *"No other leaf category of this type to move the postings to — create one first."*
That doesn't make sense:

1. There are no postings — the category was just created and no transactions have been entered
   since.
2. There are several other income categories available. Why can't the postings move to one of
   those?

(Point 1 is now `category-management/06`. Point 2 is this ticket.)

## What actually happens (confirmed against the dev database)

`CategoryService.deleteTargetOptions` filters candidates through `isLeafAfterDeletion`, which counts
**every** live child — including `CurrencyLeafService`'s hidden auto-managed per-currency leaves:

```java
private boolean isLeafAfterDeletion(long accountId, Set<Long> deletedSubtree) {
  return accountService.findChildrenOf(accountId).stream()
      .allMatch(child -> deletedSubtree.contains(child.accountId()));
}
```

This is deliberate and unit-tested (`CategoryServiceTest
.deleteTargetOptionsExcludesCategoryThatStillHasCurrencyLeafChildren`) — reassigning postings
straight onto a parent would violate leaves-only (data-model §5). `DeletionService` enforces the
same rule server-side, so this is not a UI-only filter. But the consequence in a real
multi-currency book is that the target list empties out completely. The dev database's income side:

| id | name | live children | postings |
|----|------|---------------|----------|
| 10 | Salary | 4 (all currency leaves: CHF/CZK/EUR/GBP) | 0 |
| 13 | Bottle deposit returns | 5 (all currency leaves) | 0 |
| 41 | Interest | 2 (all currency leaves) | 0 |
| 95 | Found on the street | 0 | 0 |

Every real income category has been posted to in at least one currency, so every one of them has
currency-leaf children and is excluded. The currency leaves themselves are excluded too (they never
appear in `manageableCategories()`). Category 95 is the subtree root being deleted, so it's
excluded as well — the list is empty and the form never renders.

The general shape: **once a category has been posted to in any currency, it can never again serve
as a delete target.** In a book that has been in use for a while that's every category, so
categories of that type become permanently undeletable. Same mechanism applies to `expense`.

## Why the "not a safe target" reasoning is too strict

The exclusion protects leaves-only, but the project already has the mechanism that makes a parent a
perfectly good semantic target: `CurrencyLeafService.resolveCurrencyLeaf(categoryId, currencyCode)`
routes a posting to the right per-currency leaf, creating it on first use (data-model §6.5). It is
what the entry dock uses on every commit — the user picks `Food`, the engine picks `Food/EUR`.

Reassignment should do the same thing: for each posting being moved, resolve the target category
against **that posting's currency** and file it on the resolved leaf, rather than refusing to offer
the parent at all. That also matches the owner's intuition in the report — "move it to another
income category" is a semantic choice, and which currency leaf it lands on is not the user's
problem.

## Triage — 2026-08-22

> *This was generated by AI during triage.*

**Verified.** Both halves of the original ticket were confirmed by reading the full delete path.
For this half: `isLeafAfterDeletion` counts currency-leaf children, `manageableCategories()` filters
currency leaves out of the offer list, and `DeletionService` re-enforces the same leaf rule on
commit — so a posted-to category is excluded as a target and its leaves are never offered in its
place. The behaviour is locked in by `CategoryServiceTest
.deleteTargetOptionsExcludesCategoryThatStillHasCurrencyLeafChildren`, which the fix must invert.

**The codebase already disagrees with itself.** `CategoryService.insertCategory` distinguishes real
children from currency leaves —

```java
boolean parentHasRealChildren = children.stream().anyMatch(c -> !c.currencyLeaf());
```

— so the **create** path treats "only currency leaves" as still effectively a leaf, while the
**delete** path treats the same shape as "not a leaf". An internal inconsistency, not only a
strictness judgement.

**A third defect, found during triage and folded in.** A posting carries no currency of its own —
`posting.amount` is in the native currency of its account, so a posting's currency *is* its
account's `currency_code`. Nothing in the delete path checks the target's currency:
`deleteTargetOptions` filters on type and leaf-ness, `DeletionService` re-validates only leaf-ness.
Every offerable target is a base-currency category, while a deleted subtree can hold
foreign-currency leaves. **Reassigning a subtree containing a CHF leaf onto a base-EUR target
silently reinterprets those amounts as EUR** — no exception, no trace, the numbers just change
meaning. This has been reachable since category deletion shipped (plan stage 6c). Per-currency
routing is the fix for this as much as for the reported symptom.

**A fourth, smaller gap, also folded in.** `DeletionService` never validates that the target is a
category at all, nor that its type matches; `CategoryService.deleteCategory` calls
`requireManageable` on the subtree root only. A hand-crafted POST can therefore reassign expense
postings onto an asset account such as Cash. Low practical risk on a single-user LAN deployment,
but CLAUDE.md §1.7 puts invariants in the service layer, and the MCP surface is planned to call
`operations` directly.

**Redundancy / prior-rejection check:** searched by concept for an existing implementation of
per-currency reassignment on the delete path and for prior rejections — none. There is no
`.out-of-scope/` directory in this repo.

### Decisions (grilled with the owner, 2026-08-22)

1. Reassignment becomes **currency-preserving**, routed through `CurrencyLeafService`.
2. An eligible target is one with **no real children** after the deletion — genuine groups excluded.
3. Subdividing the chosen target is **silent** — it is the ordinary §6.5 event and its leaves are
   hidden from every surface anyway.
4. `DeletionService` **validates its own target** rather than trusting the offer list.
5. The live book is **checked for existing damage before shipping**, not repaired by migration.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** Route category-delete reassignment to the target's per-currency leaf, so a posted-to
category can be a target again and a foreign-currency posting is never re-filed as base currency.

**Current behavior:**
Deleting a category moves every posting in its subtree onto one chosen target leaf with a single
bulk update. Two consequences:

- The offer list excludes any category that has live children, counting the auto-managed
  per-currency leaves that appear the first time a category is spent in a currency. In a book with
  more than one currency every real category eventually has them, so the list empties and
  categories of that type become permanently undeletable, with no workaround from the UI.
- The target's currency is never compared to the sources'. Because a posting's amount is in its
  account's native currency, moving a CHF posting onto a base-EUR target silently reinterprets it
  as EUR.

**Desired behavior:**
The user picks a target *semantically*, the way the entry dock's category field works: they choose
`Snacks`, and the engine decides which leaf each posting lands on. For every currency that actually
carries postings in the subtree being deleted, the target's leaf for that currency receives that
currency's postings, created on first use exactly as a first spend in a new currency would. No
posting ever changes the currency it is denominated in, and no posting lands on a non-leaf.

A category is an eligible target when, after the deletion, it has **no real children** — a childless
leaf, or a parent whose only children are auto-managed currency leaves. A genuine group with real
subcategories remains ineligible. This is the same predicate the category *create* path already
applies when deciding whether a parent needs subdividing, and the two paths must agree.

**Key interfaces:**

- `CategoryService.deleteTargetOptions` — its leaf test must ignore auto-managed currency-leaf
  children and count only real ones. Currency leaves themselves are still never offered under their
  own identity.
- `DeletionService.deleteCategory` — takes over currency routing, and validates its own target:
  live, an income/expense account, same type as the subtree root, outside the subtree, and with no
  real children after deletion. It must reject an ineligible target rather than rely on the offer
  list having filtered it.
- `CurrencyLeafService.resolveCurrencyLeaf` — reused unchanged. Note its unwritten contract: its
  "already a parent" branch returns the first child matching the requested currency **without
  checking that the child is a currency leaf**, so handing it a genuine group would file postings
  under an arbitrary real subcategory. It is safe today only because the dock refuses a group before
  calling it. Decision 2 keeps it safe here; if that contract is ever widened, this caller must be
  revisited.
- The account query surface — grouping needs each subtree account's `currency_code`, but the
  existing subtree walker returns ids only. It needs a sibling that returns the account rows. Per
  CLAUDE.md §6 a recursive CTE is SQL-resident logic, so it belongs in `sqlLogicTest` beside the
  existing walkers.
- `PostingReassignmentRepository` — its set-based "many sources → one target" method can stay as
  it is, called once per currency with that currency's source accounts. No per-posting update is
  needed, because a posting's currency is its account's.

**Implementation constraints (these are correctness, not style):**

- **Resolve and reassign one currency at a time, in sequence.** Resolving every currency up front
  and then reassigning is wrong: resolving a second currency can promote the target from a leaf to a
  parent, which invalidates a target id resolved earlier, and the postings then land on a non-leaf.
  Done sequentially, a later subdivision correctly carries the already-reassigned postings with it.
- **Only currencies that actually carry postings.** An empty currency leaf in the subtree must not
  cause a leaf to be provisioned on the target — leaves appear only when spent (data-model §6.5).
- Voided postings move with the rest; `deleted_at` and lifecycle are orthogonal, and the existing
  reassignment already ignores both.

**Acceptance criteria:**

- [ ] A category whose only children are auto-managed currency leaves is offered as a delete target,
      and accepted server-side.
- [ ] A category with real subcategories is neither offered nor accepted as a target.
- [ ] The reported case reproduces green: on a book where every income category has been spent in at
      least one currency, deleting an income category offers the other income categories.
- [ ] Deleting a subtree holding postings in more than one currency files each posting on the
      target's leaf for that posting's own currency; every reassigned amount keeps its original
      currency.
- [ ] After any such deletion, no posting references a non-leaf account — assert against the
      leaves-only invariant, not just the happy path.
- [ ] After any such deletion, no transaction becomes cross-currency without a frozen `base_amount`
      on every leg — assert against the conditional sum-to-zero invariant.
- [ ] A target whose currencies already cover the subtree is not subdivided and gains no new leaf.
- [ ] An empty currency leaf in the subtree provisions nothing on the target.
- [ ] `DeletionService` rejects a target that is not a category, is of the wrong type, is inside the
      subtree, or still has real children — independently of what the offer list would have shown.
- [ ] The order of resolve-then-reassign per currency is pinned by a test (Mockito `InOrder` in the
      unit tier — CLAUDE.md §6's second sanctioned exception, an ordered multi-repository sequence).
- [ ] `CategoryServiceTest.deleteTargetOptionsExcludesCategoryThatStillHasCurrencyLeafChildren` is
      inverted to assert the new rule, paired with a new case asserting a genuine group is still
      refused — so the pair reads as the new spec rather than a weakened test.
- [ ] `./gradlew check` is fully green, with no tool weakened and no suppression added.

**Pre-flight before shipping — DONE 2026-08-22, both books clear. No action needed.**

Dev book (`hauptbuch-postgres`, 575 postings / 163 transactions): **0 sum-to-zero violations, 0
leaves-only violations.** No existing damage. Exactly one category has ever been deleted in this
book — `FastFood` (expense, EUR, child of account 19; deleted 2026-07-13) — a plain single-currency
leaf, so its postings were reassigned EUR→EUR and the cross-currency path was never exercised.

Pi book: no category has ever been deleted there (owner, 2026-08-22), so the reassignment path has
never run and there is no exposure — no query needed.

For reference, should this ever need re-checking: the detector is the sum-to-zero invariant query
that `InvariantSqlLogicTest` owns as a test constant. A leg mis-filed onto a different-currency leaf
shows up as a cross-currency transaction with a missing `base_amount`. There is no automatic repair
— reassignment overwrites `account_id`, so a hit would have to be re-filed by hand.

**Out of scope:**

- Deleting a category that carries no postings at all — that is `category-management/06`, now
  **resolved** (landed 2026-08-22). The two are independent; 06 landed first. Note its one shape
  change: `CategoryService.deleteTargetOptions` is now `CategoryService.deletePanel`, returning a
  `CategoryDeletePanel(needsTarget, targets)` record. The leaf-eligibility logic this ticket must
  change (`isLeafAfterDeletion`) is unchanged and still private to `CategoryService`;
  `DeletionService.deleteCategory` now takes a nullable `Long targetLeafId`, so this ticket's
  target validation applies whenever a target *is* supplied.
- Changing category deletion from soft to hard, or adding reopen/undo for categories.
- Widening `resolveCurrencyLeaf`'s contract to accept genuine groups.
- Surfacing currency leaves anywhere in the UI — they stay hidden (data-model §6.5).
- Any change to the entry dock's own category resolution.
