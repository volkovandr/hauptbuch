# Deleting a category with no postings still demands a reassignment target

> *This was generated by AI during triage.*

Status: ready-for-agent
Category: bug
Severity: medium
Area: Category management — `DeletionService.deleteCategory`, `CategoryService.deleteCategory`,
categories controller delete endpoint, category-edit delete panel

Split out of `category-management/05` during triage on 2026-08-22. That ticket stacked two
independent defects; this is the first, and it is fixable on its own with no domain decision
pending. The second (a posted-to category can never be offered as a delete target) stays on 05.

## Reported symptom

The owner created a new income category, then tried to delete it immediately. The screen refused
with *"No other leaf category of this type to move the postings to — create one first."* The
category had been created seconds earlier and carried zero postings — there was nothing to
reassign, so it should never have been asked for a target at all.

## Confirmed cause

The delete path takes a reassignment target unconditionally, at every layer:

- the controller's delete endpoint binds `targetLeafId` as a required request parameter;
- `DeletionService.deleteCategory(subtreeRootId, targetLeafId)` resolves and validates the target
  before doing anything else;
- the category-edit delete panel renders the whole form only when the target list is non-empty,
  and otherwise shows the "create one first" message above.

Nothing anywhere asks whether the subtree carries any postings. Verified by reading the full delete
path — there is no code path that deletes a category without a target.

This is independent of 05: even once targets are offerable again, an empty category would still
force the user to pick an arbitrary destination for postings that do not exist.

## Agent Brief

**Category:** bug
**Summary:** A category subtree with no postings should delete outright, with no reassignment
target asked for or required.

**Current behavior:**
Category deletion always requires a surviving leaf to reassign postings onto. The requirement is
enforced at the controller (required request parameter), in the deletion domain operation
(the target is resolved and validated unconditionally), and in the UI (the delete form is hidden
entirely when no target can be offered). A category that has never been posted to is therefore
undeletable whenever no eligible target exists, and needlessly asks for a destination even when
one does.

**Desired behavior:**
If no posting — live or voided — has ever hit any account in the subtree being deleted, the
category deletes with no target: the UI shows the delete action with no picker, and the domain
operation accepts an absent target. If the subtree does carry postings, today's behaviour is
unchanged: a target is required, and it must still be a live leaf outside the subtree. An absent
target on a subtree that has postings is an error, not a silent posting drop.

**Key interfaces:**
- `DeletionService.deleteCategory` — must accept an absent target (an overload, or a nullable
  parameter). Absent target with a posting-carrying subtree throws `IllegalArgumentException`;
  the existing target validation (exists, is a leaf after deletion, outside the subtree) applies
  unchanged whenever a target is supplied.
- `CategoryService.deleteCategory` — mirrors that shape. Its INFO "Category deleted" log and its
  sweep of the subtree's AI-vocabulary config rows must happen on the no-target path too.
- `AccountService` / the accounts repository — needs a batched "has any posting ever hit any of
  these accounts" query. The existing single-account `hasPostings` is the right semantics to
  preserve: it counts **live and voided** postings alike. Per CLAUDE.md §6 this is a simple
  `exists` over one table, so it belongs in the integration tier as a round-trip, not
  `sqlLogicTest`.
- The categories controller's delete endpoint — `targetLeafId` becomes optional.
- The category-edit delete panel — needs to know whether a target is required, so the model needs
  that flag alongside the existing target list. Render the delete form with no picker when the
  subtree is empty; the "create one first" message must appear only when a target is genuinely
  needed and none can be offered.

**Acceptance criteria:**
- [ ] A category whose subtree carries no postings deletes successfully with no target supplied,
      regardless of whether any eligible target exists.
- [ ] The reported case reproduces green: a just-created, never-posted-to category deletes from the
      category edit screen without being asked for a destination.
- [ ] A category whose subtree carries postings still requires a target, and still refuses a target
      that is inside the subtree or is not a leaf after deletion.
- [ ] Supplying no target for a subtree that carries postings is rejected with a clear message —
      postings are never dropped.
- [ ] A subtree whose only postings are voided counts as non-empty and still requires a target.
- [ ] Soft-delete of the whole subtree and the AI-vocabulary config sweep both still happen on the
      no-target path.
- [ ] The "No other leaf category of this type to move the postings to" message no longer appears
      for an empty category.
- [ ] `./gradlew check` is fully green, with no tool weakened or suppression added.

**Out of scope:**
- Target eligibility — which categories may be *offered* as a destination, and the currency-leaf
  exclusion that empties the list. That is `category-management/05`, still in triage.
- Changing category deletion from soft to hard, or adding a reopen/undo for categories.
- Account deletion — accounts close and reopen, they are not deleted.
