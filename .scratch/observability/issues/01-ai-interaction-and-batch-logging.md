# AI-interaction and batch logging for receipts (it costs money)

Status: resolved
Category: enhancement
Severity: high
Area: Receipts — AI parser + batch client (`ReceiptAnalyser`, `AnthropicReceiptParser`,
`ReceiptBatchAnalyser`, `AnthropicReceiptBatchClient`)

## Request (owner)

The app has no deliberate logging strategy today — just Spring Boot's defaults. Priority one: log
every interaction with the AI provider, because those calls cost real money and there's currently
no log trail of a call happening at all, only the DB row it leaves behind.

## What exists today

- `AnthropicReceiptParser.parse` (the single-mode Messages call) has **no logging at all** —
  success or failure.
- `ReceiptAnalyser.run` logs `WARN`/`ERROR` only on failure, with no cost/token/duration detail.
- `ReceiptAnalyser.applyParsed` is the shared landing point for single-mode, an operator's
  re-parse, and the 9h batch poller — it has no logging.
- `AnthropicReceiptBatchClient` logs `WARN` only on a failed poll attempt.
- `ReceiptBatchAnalyser` logs `WARN`/`ERROR`/`INFO` around submit/poll failures and a
  stranded-batch warning, but nothing on a normal submit or a normal finish.

## Agent Brief

**Category:** enhancement

**Summary:** Add DEBUG-level request/response logging and INFO-level outcome logging around every
AI call the receipts module makes — single-mode Messages calls and Batches API submit/poll — so
the cost-driving calls are visible in the logs without a DB query.

**Desired behavior:**

Level ladder (see `CLAUDE.md` §5 "Logging" — agreed for the whole app, not just this ticket):
ERROR = unexpected bug, WARN = handled failure, INFO = rare/structural business event worth a
permanent record, DEBUG = verbose diagnostic, off by default.

For AI calls specifically:

- **DEBUG, request sent** — logged just before the call: model id, the `cachePrompt`/batch flag,
  the system prompt text (including the AI Vocabulary — this is parsing instructions, not ledger
  content, so logging it is fine under ARCH-08) and the AI note text. **Never the image bytes**
  (owner-agreed: impractical size, no diagnostic value) and never the API key.
- **DEBUG, response received** — logged right after: the full raw response text (the TOON body) —
  this is the actual diagnostic payload. On failure, log whatever came back, same spirit as today's
  `WARN`.
- **INFO, processing finished (success only)** — receipt id, token counts, and `parse_cost`.
  **Must NOT fire for a batch member.** Since `applyParsed` (the shared landing function) is called
  by both the single-item paths and the batch poller's per-member loop, do **not** put this INFO
  log inside `applyParsed` itself — log it in the two single-item callers instead: `ReceiptAnalyser
  .run` (after `parseAndSeed` succeeds) and `ReceiptAnalyser.reparse` (after a successful re-seed,
  even though no fresh API call was made — it's still "processing finished" for that receipt, using
  the carried-over token counts and frozen cost). The batch poller's call into `applyParsed` gets no
  per-member log at all.
- **INFO, batch submitted** — once per `Process` action: batch id, receipt count, model, and
  cached=true (batch always caches per stage 9h).
- **INFO, batch finished** — once when the poller lands a batch's final state: batch id, receipt
  count, succeeded/failed counts, total tokens (summed across members), total cost (summed), and
  elapsed time since submit if that's cheap to compute from data already on hand — otherwise omit
  the duration rather than adding new state just to compute it.
- The existing `WARN`/`ERROR` failure logs stay as they are — this ticket adds INFO/DEBUG around
  them, it doesn't restructure them.

**Key interfaces:**
- `AnthropicReceiptParser.parse` — wrap the `clients.forKey(...).messages().create(params)` call
  with DEBUG request/response logging. Add a `Logger LOG` field (none exists yet).
- `AnthropicReceiptBatchClient` — same DEBUG shape around its submit/poll SDK calls (already has a
  `Logger`).
- `ReceiptAnalyser.run` / `ReceiptAnalyser.reparse` — add the INFO "processing finished" log after
  a successful `applyParsed` (already has a `Logger`).
- `ReceiptBatchAnalyser` — add INFO logs at the submit call site and the poll-success call site
  where a batch's final state is determined, aggregate-only (already has a `Logger`).

**Acceptance criteria:**
- [ ] A single-mode Analyse call logs a DEBUG request line (model, cache flag, system prompt, note
      — no image bytes, no API key) and a DEBUG response line (full raw text) around the SDK call
      in `AnthropicReceiptParser`.
- [ ] A successful single-mode or re-parse outcome logs one INFO line with receipt id, token
      counts, and cost.
- [ ] A batch submit logs one INFO line (batch id, count, model); nothing per-receipt.
- [ ] A batch finishing logs one INFO line (batch id, counts, total tokens, total cost); nothing
      per-receipt, even though `applyParsed` runs once per member.
- [ ] Existing WARN/ERROR failure logging is unchanged in behavior (still fires on the same
      conditions).
- [ ] No log line ever contains the AI API key or the raw image bytes.
- [ ] `./gradlew check` green (Checkstyle/PMD/SpotBugs pass on the new logger usage — parameterized
      messages, no string concatenation).

**Out of scope:**
- Structured/JSON logging, correlation ids, custom file appenders/rotation — journald on the Pi
  already covers this (owner-agreed).
- Dedicated tests asserting log line content — no existing call site in the codebase is tested this
  way today (the existing WARN/ERROR logs have no test coverage either); this ticket doesn't
  introduce a new "logging" test tier. `parse_cost`/the token-count DB columns remain the tested
  source of truth for cost correctness.
- Person/account/category/receipt create-delete logging — sibling ticket `observability/02`.
- Transaction record/edit/void logging — sibling ticket `observability/03`.
