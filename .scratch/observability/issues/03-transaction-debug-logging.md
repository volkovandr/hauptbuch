# Transaction DEBUG logging (record / edit / void)

Status: ready-for-agent
Category: enhancement
Severity: high
Area: `ledger` — `LedgerService`

## Request (owner)

A new transaction entered is rather a DEBUG-level event, not INFO — it's the routine, high-frequency
operation of the app, unlike creating a person/account/category. Transaction details are not
logged, but the id and total amount should be.

## What exists today

`LedgerService.recordTransaction`, `editTransaction`, and `voidTransaction` log nothing today.

## Comments

Filed 2026-08-21, triaged the same day as a sibling of `observability/01` (AI/batch logging) and
`observability/02` (create/delete logging) — see `CLAUDE.md` §5 "Logging" for the shared level
ladder. The DEBUG-not-INFO choice for transactions, confirmed by the owner, generalizes: any future
high-frequency operation gets the same shape (DEBUG, id + the one identifying amount if there is
one, no further detail) rather than being re-decided per operation.

## Agent Brief

**Category:** enhancement

**Summary:** Log every transaction record/edit/void at DEBUG, with only the transaction id and its
total amount — never per-posting/leg detail (no category, account, tag, or note content).

**Desired behavior:** each of the three `LedgerService` methods logs one DEBUG line on success:
- `recordTransaction` → `"Transaction recorded: id={}, total={}"`
- `editTransaction` → `"Transaction edited: id={}, total={}"` (the *new* total, post-edit)
- `voidTransaction` → `"Transaction voided: id={}"` (voiding doesn't change the total, so id alone
  is enough)

"Total" = the transaction's absolute posting total, using whatever helper `LedgerService` already
has for that (check before adding a new one) — no per-posting/per-leg detail, matching the owner's
explicit "transaction details are not logged" rule.

Since `recordTransaction`/`editTransaction`/`voidTransaction` are the single engine-level choke
point — `operations.DockCommitService`, `receipts.ReceiptCommitService`, and
`ledger.LedgerOpeningBalanceRecorder` all ultimately call through them — logging here, and only
here, covers every caller (dock entry, receipt confirm, opening balance) without a duplicate line
per entry surface.

**Key interfaces:** `LedgerService.recordTransaction`, `LedgerService.editTransaction`,
`LedgerService.voidTransaction`. Add a `Logger LOG` field (none exists in this class yet — confirm
at implementation time).

**Acceptance criteria:**
- [ ] Committing a transaction from the dock, from a receipt confirm, or as an opening balance all
      produce exactly one "Transaction recorded" DEBUG line via the shared `LedgerService
      .recordTransaction` choke point — not one line per entry surface.
- [ ] Editing a transaction logs one "Transaction edited" DEBUG line with its new total.
- [ ] Voiding a transaction logs one "Transaction voided" DEBUG line.
- [ ] No posting-level, category, account, tag, or note content ever appears in these lines.
- [ ] With logging left at its default level (DEBUG off), none of these lines appear in normal
      operation.
- [ ] `./gradlew check` green.

**Out of scope:**
- AI-interaction/batch and create-delete logging — tickets `observability/01` and
  `observability/02`.
- Any change to what `recordTransaction`/`editTransaction`/`voidTransaction` actually do — logging
  only.
