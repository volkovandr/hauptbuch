# Landing page: QR code to open the app on the phone

Status: ready-for-agent
Category: enhancement
Severity: low
Area: Landing page (`ledger`), UI shell (`web`), Pi deployment (`deploy/`)

Getting the app open on the phone means typing its URL by hand, and the URL is deployment-specific:
it may be `http://raspberrypi:8080/`, a bare `http://192.168.1.14:8080/`, or — behind a home gateway
— `http://homenet/pi/hauptbuch/`. Render a QR code of the app's own phone-reachable URL on the
landing page so the phone gets there by camera instead of by typing.

The phone is already the capture device: `LandingController` redirects a `Mobi` User-Agent from `/`
straight to `/receipts/capture`, so a scan of the app root lands the phone on the capture surface
with no further navigation.

Decided with the owner 2026-08-30 (see `## Comments`). Third landing-page issue, after `01` (pinned
balances) and `02` (tracking stats).

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Resolve the app's externally-reachable base URL from the incoming request (honouring a
gateway's `X-Forwarded-*` headers), with a config override for the case the gateway can't be made to
send them, and render it as an inline-SVG QR code in an "Open on your phone" panel at the bottom of
the landing page.

**Current behavior:**
`LandingController` (in `ledger`) renders `landing.html`: the eyebrow/greeting/lede `leaf-head`, the
lazy-loaded tracking-stats line, the Balances panel (issue `01`), and — only before the base currency
is set — the first-run panel. Nothing anywhere in the app tells the operator what URL it is reachable
at; `web` contains only `NavItem` and `GlobalHtmxErrorAdvice`. `server.forward-headers-strategy` is
unset, so Spring's `ForwardedHeaderFilter` is **not** installed and `X-Forwarded-*` headers from a
gateway are ignored.

**Desired behavior:**

*Resolving the URL* — in this order, first hit wins:

1. **Config override.** `hauptbuch.public-base-url`, unset by default. When set and non-blank it is
   used verbatim (normalised to exactly one trailing `/`). This is the escape hatch for a gateway
   that cannot be made to send `X-Forwarded-Prefix`, and for any other case the derived value is
   wrong. No validation beyond "parses as an absolute http(s) URI"; a bad value is the operator's
   problem, and it is their own landing page.
2. **Derived from the current request.** Scheme, host, port and context path of the request that is
   rendering the landing page — i.e. the URL the desktop browser is *already* reaching the app at,
   which is by construction one that resolves on the same LAN. The port is omitted when it is the
   default for the scheme (80/443). Always ends in exactly one `/`; never carries the request's own
   path beyond the context path, or its query string.
3. **Nothing.** If the resolved host is a loopback address (`localhost`, anything in `127.0.0.0/8`,
   `::1`) the panel does not render at all — a QR of `http://localhost:8080/` is useless on a phone,
   and dev is exactly where that happens. No placeholder, no hint, no empty panel.

To make step 2 work behind a gateway, set `server.forward-headers-strategy: framework` in
`src/main/resources/application.yaml`. That installs Spring's `ForwardedHeaderFilter`, which rewrites
the request from `X-Forwarded-Proto` / `-Host` / `-Port` / `-Prefix` before it reaches the controller
— so the resolver reads plain `request.getScheme()` / `getServerName()` / `getServerPort()` /
`getContextPath()` and needs no header handling of its own. With no proxy in front the headers are
absent and the filter is a no-op, so this is safe in dev and on a direct-to-Pi deployment.

Worked examples (request → encoded URL):

| Request the desktop made | Encoded |
|---|---|
| `http://raspberrypi:8080/` | `http://raspberrypi:8080/` |
| `http://192.168.1.14:8080/register?accountId=3` | `http://192.168.1.14:8080/` |
| `http://homenet/register` + `X-Forwarded-Host: homenet`, `X-Forwarded-Prefix: /pi/hauptbuch` | `http://homenet/pi/hauptbuch/` |
| `http://localhost:8080/` | *(no panel)* |
| any, with `hauptbuch.public-base-url: http://homenet/pi/hauptbuch` | `http://homenet/pi/hauptbuch/` |

*Rendering the QR* — `com.google.zxing:core` (pure Java, no transitive dependencies). Add **only**
`core`; do **not** add `com.google.zxing:javase`, which drags in `ImageIO`/AWT for raster output we
do not want. Encode with `QRCodeWriter` at error-correction level **M** and a quiet zone of 4 modules
(ZXing's `MARGIN` hint), then walk the `BitMatrix` and emit an inline `<svg>`:

- `viewBox="0 0 N N"` where `N` is the matrix size, one `<rect width="1" height="1">` (or one merged
  `<path>`) per dark module — the geometry is in module units, so the CSS size is a single
  `width: 140px; height: auto` on the element.
- `shape-rendering="crispEdges"`, plus `role="img"` and a `<title>` naming the URL for screen readers
  (HTML-escaped — it is the only interpolated value in the markup).
- **Fixed dark-on-light**, not theme colours: a full-size light background rect under near-black
  modules, regardless of the page theme. Scanner reliability beats theme fidelity, and an inverted QR
  is not universally readable.
- The SVG string is generated by us and inlined with `th:utext`.

*The panel* — a single `.panel` at the **bottom** of `landing.html`, after the Balances panel and the
first-run panel, in the existing house style:

- `<p class="eyebrow">Open on your phone</p>`, the QR, and beneath it the encoded URL as selectable
  plain text, so it can also just be read off and typed.
- Rendered whenever a URL resolves — independent of `baseCurrencySet` (unlike the Balances panel).
- One line of muted copy is enough context; no instructions, no "how to scan" prose.

**Key interfaces:**
- **`web`** is where this lives — it is UI-shell infrastructure with no domain content, and
  `ledger.LandingController` already depends on `web.NavItem`, so the module edge exists and
  `ApplicationModules.verify()` stays green. Public top-level types in `web`: a `PhoneQrCode` record
  (`url` + `svg`) and the service that produces it, e.g.
  `PhoneQrCodeService.forRequest(HttpServletRequest) : Optional<PhoneQrCode>`. Push the URL resolution
  and the SVG emitter into a module-internal sub-package (e.g. `web.qr`).
- Take the `HttpServletRequest` as a **parameter** rather than reaching for `RequestContextHolder` /
  `ServletUriComponentsBuilder.fromCurrentRequest()` — explicit, and unit-testable with
  `MockHttpServletRequest`.
- `LandingController` — adds `@RequestParam`-free plumbing only: take the request, call
  `phoneQrCodeService.forRequest(request).ifPresent(qr -> model.addAttribute("phoneQrCode", qr))`,
  mirroring how `balancesPanelService.current()` is already wired.
- `build.gradle` — the one new `implementation` dependency.
- `src/main/resources/application.yaml` — `server.forward-headers-strategy: framework`, with a comment
  saying why (gateway path-prefix deployments) and that it is a no-op without a proxy.
- `deploy/application.yml.example` — a commented-out `hauptbuch.public-base-url` with a one-line
  explanation. `deploy/README.md` — a short note that a gateway should pass `X-Forwarded-Proto`,
  `X-Forwarded-Host` and `X-Forwarded-Prefix`, and that the property is the fallback when it can't.
- `docs/tech-stack.md` — the ZXing decision with its rejected alternatives (§4 subsection + a §8 row).
- No migration, no schema change, no new table — nothing here is persisted.

**Acceptance criteria:**

      quality tool.
- [ ] Unit tests on the URL resolver, one case per row of the table above, plus: the override wins
      over a perfectly good derived URL; a blank override is ignored; `127.0.0.1` and `::1` are

- [ ] Unit test on the SVG emitter: the module count matches the matrix, the markup is well-formed,
      the URL appears escaped in `<title>`. A genuine encode→decode round-trip (a ~20-line test-only

      only thing that actually proves the QR says what we think it says.
- [ ] Integration test (MockMvc, real Postgres, alongside `LandingBalancesPanelIntegrationTest`): the
      panel renders an `<svg>` and the URL text for a normal `Host`; it is absent for a loopback
      `Host`; `X-Forwarded-Host` + `X-Forwarded-Prefix` produce the gateway URL — which is the test
      that proves `forward-headers-strategy` is actually wired, not just configured; the property
      override wins.
- [ ] No `sqlLogicTest` — there is no SQL in this feature.
- [ ] All copy English; the panel matches the existing `.panel` / `.eyebrow` house style.
- [ ] `CONTEXT.md` "Phone QR panel" / "Public base URL" terms added during triage — keep the
      implementation consistent with them.

**Out of scope:**
- HTTPS (ARCH-05) and any auth token or one-time pairing link in the QR (ARCH-04 does not exist; the
  deployment is LAN-only and unauthenticated by decision — the QR grants nothing that the LAN did not
  already grant).
- Scanning **NIC addresses** to invent a LAN URL when the request came in on loopback. Considered and
  rejected: it guesses on a multi-homed host, and the config override already covers every case where
  the request cannot answer the question.
- Deep-linking the QR at anything but the app root (the `Mobi` redirect already routes the phone to
  capture), a "copy link" button, downloading or printing the QR, and any caching of the SVG —
  encoding one QR per landing render is microseconds.
- Showing the panel on the phone itself (the phone never sees the landing page — it is redirected).
- Discovering or advertising the app over mDNS/Bonjour.

## Comments

> *This was generated by AI during triage.*

Filed 2026-08-30 by the owner: the landing page should carry a QR that opens the app on the phone,
and it has to cope with the deployment being at a hostname, a bare IP, or behind a gateway with a
path prefix.

Decisions taken the same day:
- **URL source:** derive from the incoming request, honouring `X-Forwarded-*` via
  `server.forward-headers-strategy: framework`; `hauptbuch.public-base-url` overrides when set;
  loopback renders nothing.
- **QR library:** ZXing `core` only, rendered as inline SVG. The client-side JS route is barred by
  CLAUDE.md §1.6 (bespoke JS lives in the two sanctioned leaves), and hand-rolling a QR encoder is a
  few hundred lines of Reed-Solomon and masking to own forever for one code on one page.
- **Placement:** a small `.panel` at the bottom of the landing page, QR plus the URL in plain text.
- **Trust:** `X-Forwarded-*` are spoofable by anything that can reach the app directly. Accepted —
  the app is LAN-only and single-user, and the worst case is a wrong QR on the operator's own landing
  page. No redirect or auth surface consumes these values.
