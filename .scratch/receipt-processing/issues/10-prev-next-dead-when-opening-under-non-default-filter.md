# Prev/Next go dead when opening a receipt from the list under a non-default filter (e.g. Committed)

Status: resolved
Category: bug
Severity: medium
Area: Receipts — register list → processing screen open link (`receipts.html`/
`ReceiptProcessingController`/`keyboard.js`)

## Symptom (owner report)

Set the list filter to **Committed** and press Apply — the filtered list correctly shows only
committed receipts. Open any one of them: Prev/Next are both dead (and so are the ↑/↓ shortcuts).
Under the default **Work queue** filter, Prev/Next work fine.

## What exists today

This reproduces on first open, with no commit action involved — a different mechanism from the
already-resolved issue 05 (`.scratch/receipt-processing/issues/05-prev-next-disabled-after-commit.md`),
which was about `neighbours` being recomputed *after* a commit against the filter the receipt just
left.

- The list row's open link drops the active filter entirely: `receipts.html:120` —
  `th:attr="data-receipt-open=@{/receipts/{id}(id=${r.receiptId()})}"` — carries no `state`/`range`
  query params, unlike every other action in the same template, which passes
  `hx-include="... [name='state'], [name='range']"` (e.g. `:171, 217, 271, 282`).
- Row activation (Enter, double-click) navigates straight to that param-less URL:
  `keyboard.js:83-84` and `:488-490` both do `window.location.href = row.dataset.receiptOpen`.
- `ReceiptProcessingController.screen` (`ReceiptProcessingController.java:77-98`) declares `state`
  as `@RequestParam(required = false, defaultValue = ReceiptFilters.STATE_QUEUE)` (`:80`) — so with
  no `state` param on the URL, it silently defaults back to `"queue"`, regardless of what filter
  was actually active on the list the user came from.
- `addChrome` (`:510-520`) computes `neighbours` using that defaulted `state=queue`.
  `ReceiptFilters.statesFor("queue")` resolves to `ReceiptState.WORK_QUEUE`
  (`ReceiptFilters.java:31-39`, `ReceiptState.java:44-45`), which **excludes** `committed`
  (`ReceiptState.java:41-43`).
- `ReceiptService.neighbours` (`ReceiptService.java:217-227`) then scans
  `findForRegister(WORK_QUEUE, ...)` for the opened receipt's own id, never finds it (it's
  `committed`, not in the work-queue set), and falls through to `ReceiptNeighbours.NONE`
  (`ReceiptNeighbours.java:14`). Both Prev and Next render as the disabled
  `<span class="btn is-disabled">` (`receipt-process.html:317-318, 328-329`).
- **Correction (triage, 2026-08-19):** the processing screen has **no state-filter `<select>`** —
  that control only exists on the list (`receipts.html:46`). `receipt-process.html` instead carries
  the (silently defaulted) `state` value forward as plain `<input type="hidden" name="state">` on
  every action (Prev/Next links, delete, reopen, the redirect-back-after-save, etc. —
  `receipt-process.html:68,79,108,250,266,303,312,323,346-347,384,417,423,448,470,514`), all sourced
  from `model.addAttribute(STATE_FILTER, state)` (`ReceiptProcessingController.java:177, 227, 441,
  478, 518`). So there's no second *visible* symptom on this screen, but the mis-defaulted `queue`
  propagates through every one of those hidden inputs for the rest of the visit — not just the
  initial Prev/Next dead-end.

Under the **default** `queue` filter this defect is invisible, because the silently-defaulted
`state=queue` happens to match the filter that was actually active — which is why the owner only
sees this under Committed (or presumably any other non-default single-state filter, e.g. Failed).

## Agent Brief

**Category:** bug
**Summary:** Opening a receipt from the list under a non-default filter (e.g. Committed) loses that
filter, so Prev/Next and the ↑/↓ shortcuts go dead on the processing screen, and the lost filter
keeps propagating for the rest of the visit.

**Current behavior:**
The list's per-row open action (row click, Enter, double-click) navigates to the receipt's
processing-screen URL without forwarding the list's currently active state/range filter — unlike
every other action on the list (bulk actions, sort links, etc.), which does carry that filter. The
processing screen's request handler treats a missing filter param as an explicit request for the
default filter (work queue / 90 days), because the two are indistinguishable once the param is
absent. It then computes the prev/next neighbours over that (wrongly) defaulted filter. If the
receipt being viewed isn't in the defaulted filter's result set (true for any receipt whose real
state differs from the default, e.g. `committed`), the neighbours lookup finds nothing and both
Prev and Next render disabled — as do the ↑/↓ keyboard shortcuts. The (wrong) defaulted filter is
then threaded through every other filter-carrying control on the screen (Prev/Next links, delete,
reopen, the save-and-return redirect, etc.), so the loss isn't limited to the first render — it
persists for the rest of the visit to that receipt. This is invisible under the default filter only
because the silent default happens to match reality in that one case.

**Desired behavior:**
Opening a receipt from the list, by any activation path (click, Enter/double-click, and any
keyboard shortcut that opens a row), carries the list's currently active state and range filter to
the processing screen — the same filter values the list's other row/bulk actions already forward.
Once open, Prev/Next and ↑/↓ step through neighbouring receipts under that same actually-active
filter, and every subsequent action taken from that screen keeps carrying it correctly. Opening a
receipt with no filter context at all (e.g. a bookmarked or hand-typed URL) is a separate case and
should keep falling back to the existing default filter — that fallback itself is correct and must
not be removed, only bypassed when the list *does* have an active filter to hand off.

**Key interfaces:**
- The list row's per-row "open" URL/attribute needs to be built including the filter's current
  `state`/`range` values, the same way the list's other per-row and bulk actions already source
  those values from the filter form.
- Whatever JS reads that per-row open URL to navigate (on row activation and on the relevant
  keyboard shortcuts) should need no change if the URL itself already carries the filter — but
  confirm neither activation path drops the params separately before navigating.
- No change to the processing-screen request handler's default-value behavior itself — that default
  is the correct fallback for direct/bookmarked navigation with no filter context. The fix belongs
  entirely on the "what URL does the list navigate to" side.

**Acceptance criteria:**
- [x] Opening a receipt from the list while filtered to `committed` (or any other non-default
      single-state filter, e.g. `failed`) shows working Prev/Next buttons and ↑/↓ shortcuts that
      step through other receipts under that same filter.
- [x] Opening a receipt from the list under the default filter is unchanged (no regression).
- [x] Opening a receipt via a direct/bookmarked URL with no filter params still falls back to the
      default filter, unchanged (the controller's default-value behavior was untouched).
- [x] Both the click/Enter/double-click activation path and any keyboard-shortcut activation path
      carry the filter — not just one of the two (both read the same fixed URL, no JS change
      needed).
- [x] An automated test (integration/acceptance tier, per this project's testing conventions) covers
      opening a receipt from the list under a non-default filter and asserts the neighbours are
      resolved rather than empty.

**Out of scope:**
- The already-resolved issue 05 mechanism (neighbours going stale after a *commit* action) — a
  different code path, already fixed; do not re-touch it.
- Redesigning how the filter is represented in the URL or on the model.
- Any change to the default-filter fallback behavior for direct navigation.

## Resolution (2026-08-19)

Fixed the list row's `data-receipt-open` URL to carry the active `state`/`range` filter, mirroring
the template's other row/bulk actions. No JS or controller change was needed — both already
navigated to / handled whatever URL they were given correctly; the URL itself was the only thing
missing the filter.

A `/code-review` pass on the diff surfaced a second, independent instance of the identical bug: the
transaction register's receipt paperclip link (`register.html`) also built a bare `/receipts/{id}`
URL with no filter params. Since the paperclip always points at a `committed` receipt, that entry
point had this bug on *every* use, not just under a non-default list filter — fixed the same way
(`state=committed`, `range=all`, since the receipt's own capture date is unrelated to that jump).

Covered by three new/updated integration tests: the list row's open URL under both the default and
a non-default filter, the processing screen's neighbours resolving under a carried non-default
filter, and the register paperclip's URL now carrying its filter. `./gradlew check` green.
