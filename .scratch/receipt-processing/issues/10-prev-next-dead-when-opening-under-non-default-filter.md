# Prev/Next go dead when opening a receipt from the list under a non-default filter (e.g. Committed)

Status: needs-triage
Category: bug
Severity: medium
Area: Receipts — register list → processing screen open link (`receipts.html`/
`ReceiptProcessingController`/`keyboard.js`)

## Symptom (owner report)

Set the list filter to **Committed** and press Apply — the filtered list correctly shows only
committed receipts. Open any one of them: Prev/Next are both dead (and so are the ↑/↓ shortcuts).
Under the default **Work queue** filter, Prev/Next work fine.

## What exists today

This reproduces on first open, with no commit action involved — a different mechanism from the
already-resolved issue 05 (`.scratch/receipt-processing/issues/05-prev-next-disabled-after-commit.md`),
which was about `neighbours` being recomputed *after* a commit against the filter the receipt just
left.

- The list row's open link drops the active filter entirely: `receipts.html:120` —
  `th:attr="data-receipt-open=@{/receipts/{id}(id=${r.receiptId()})}"` — carries no `state`/`range`
  query params, unlike every other action in the same template, which passes
  `hx-include="... [name='state'], [name='range']"` (e.g. `:171, 217, 271, 282`).
- Row activation (Enter, double-click) navigates straight to that param-less URL:
  `keyboard.js:83-84` and `:488-490` both do `window.location.href = row.dataset.receiptOpen`.
- `ReceiptProcessingController.screen` (`ReceiptProcessingController.java:77-98`) declares `state`
  as `@RequestParam(required = false, defaultValue = ReceiptFilters.STATE_QUEUE)` (`:80`) — so with
  no `state` param on the URL, it silently defaults back to `"queue"`, regardless of what filter
  was actually active on the list the user came from.
- `addChrome` (`:510-520`) computes `neighbours` using that defaulted `state=queue`.
  `ReceiptFilters.statesFor("queue")` resolves to `ReceiptState.WORK_QUEUE`
  (`ReceiptFilters.java:31-39`, `ReceiptState.java:44-45`), which **excludes** `committed`
  (`ReceiptState.java:41-43`).
- `ReceiptService.neighbours` (`ReceiptService.java:217-227`) then scans
  `findForRegister(WORK_QUEUE, ...)` for the opened receipt's own id, never finds it (it's
  `committed`, not in the work-queue set), and falls through to `ReceiptNeighbours.NONE`
  (`ReceiptNeighbours.java:14`). Both Prev and Next render as the disabled
  `<span class="btn is-disabled">` (`receipt-process.html:317-318, 328-329`).
- The screen's own state-filter `<select>` is driven from the same defaulted `state` param
  (`ReceiptProcessingController.java:518`), so it would also silently read back as "Work queue"
  rather than "Committed" — a second visible symptom of the same root cause, worth confirming
  during triage.

Under the **default** `queue` filter this defect is invisible, because the silently-defaulted
`state=queue` happens to match the filter that was actually active — which is why the owner only
sees this under Committed (or presumably any other non-default single-state filter, e.g. Failed).

## Comments

Filed 2026-08-13 from an owner report. Root cause traced to the open link
(`receipts.html:120`)/row-activation JS never forwarding the active `state`/`range` filter to
`/receipts/{id}`, combined with the controller's silent `queue` default masking the loss whenever
the active filter happens to already be `queue`. Left at `needs-triage` — the likely fix (carry
`state`/`range` onto the open URL, same as the template's other actions already do) looks
straightforward, but confirming the state-filter-`<select>` misread and deciding the fix's shape is
left to triage rather than assumed.
