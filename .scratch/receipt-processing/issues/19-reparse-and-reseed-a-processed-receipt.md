# Let a `processed` receipt's AI response be viewed, edited, and re-seeded without a new AI call

> *This was generated by AI during triage.*

Status: ready-for-agent
Category: enhancement
Severity: high
Area: Receipts — processing screen (`processed` view), `ReceiptAnalyser.reparse`,
`ReceiptProcessingController`, `receipt-process.html`

## What prompted this

The owner scanned ~50 receipts from one vacation, added an AI note asking for a tag
(`Trips:France-2026`), and analysed them all as a batch. **The model returned the tag correctly on
every receipt, and not one of them got tagged.** The tag did not exist in the `tag` table yet, and
`ReceiptSeeder` resolves AI tag echoes through `TagService.resolveExistingChip` — the deliberately
**non-creating** resolver (data-model §13.3, plan stage 9d): any chip whose full `Parent:Child` path
does not already exist is dropped, silently. The owner only discovered it by reading `parse_raw` in
psql.

The tag now exists, so the responses are all still good — the information is sitting in `parse_raw`
on 50 rows, and there is currently no way to apply it short of re-running (and re-paying for) the
analysis.

Diagnosis detail, so it is not re-litigated: the TOON decode is **not** at fault. Both tags were
present and correctly quoted in `parse_raw`; the seeder splits the tags cell on `[,;]` and strips;
the lookup SQL is case-insensitive, null-parent-safe (`is not distinct from`) and live-scoped; and
line tags are inserted one per row with `on conflict do nothing`. The drop is exactly what
`resolveExistingChip` is specified to do.

## Why re-seed rather than letting the AI create tags

Auto-creating a tag from the model's echoed string would not have helped these 50 receipts at all —
they are already analysed and already seeded tag-less, so a seeding-time change only affects future
analyses. Re-seeding is needed regardless. It also keeps the tag vocabulary operator-curated
(§13.3): a hallucinated variant like `Trips:France2026` would otherwise mint a permanent second tag
that silently splits every rollup.

## Requested feature (owner, 2026-08-22)

On the `processed` view of the processing screen, **below the AI costs line**, add an expandable
panel that shows the stored AI response, lets it be edited in place, and re-parses + re-seeds the
edited text with **no new API call**. The re-parse button is inside the expander, so it is hidden
until the panel is opened.

This is deliberately **the same affordance the `failed` view already has** — the
`details`/textarea/"Parse my edited text" block added from owner feedback on 2026-08-02 — extended
to receipts that parsed successfully.

## Agent Brief

**Category:** enhancement
**Summary:** Extend the existing edit-the-AI-response-and-re-parse affordance from `failed`
receipts to `processed` ones, so a receipt can be re-seeded from its stored response after the
taxonomy it references has changed.

**Current behavior:**
A `failed` receipt's screen offers a collapsed details panel containing the returned parser text in
a textarea and a button that posts the edited text back, re-decodes it and re-seeds the receipt with
no new API call. A `processed` receipt shows only its token/cost telemetry — its stored response is
not visible in the UI at all, and there is no way to re-run seeding against it. Re-analysing (a
fresh, billed AI call) is the only option, and it is the wrong tool when the response was already
correct and only the taxonomy it referenced was missing.

**Desired behavior:**
The same panel appears on the `processed` view, below the AI-costs line, collapsed by default, with
the re-parse control inside it so nothing is clickable until the panel is opened. Submitting
re-decodes the edited text and re-seeds the receipt's draft lines from it, preserving the stored
token counts and cost — no API call, no new charge. Re-seeding replaces the draft lines, so any
manual edits to them are discarded; the panel must say so before the operator submits.

Re-seeding resolves everything the seeder resolves — tags, target accounts, person/beneficiary
matches — against the taxonomy **as it is now**. It does not re-run the model, so an edited AI note
has no effect (that is re-analysis, `receipt-processing/18`); the panel's copy should not imply
otherwise.

**Key interfaces:**
- `ReceiptAnalyser.reparse(receiptId, editedRaw)` — already does the whole job for `failed`
  receipts, and already preserves the stored token counts and cost rather than re-charging. The only
  thing preventing its use here is its state guard, which currently accepts `failed` alone. Widen it
  to accept `processed` as well. `committed` must stay excluded — its lines back a real transaction.
- The processing controller's re-parse endpoint — unchanged in shape; it should keep working for
  both states.
- The processing screen's `processed` view — gains the panel. The `failed` view's existing block is
  the pattern to follow: a plain `details` element, no JS (CLAUDE.md §1.6).
- `ReceiptAnalysisService.applyProcessed` — already clears the receipt's draft lines before
  re-seeding, so no new clearing logic is needed.

**Behaviour to decide in code, called out so it is not an accident:**
If the edited text does not decode, the existing path fails the receipt (`failUndecodable`), keeping
the edited text — which means a bad edit moves a `processed` receipt into `failed`. That is
acceptable and recoverable (the `failed` view is exactly the repair surface, and it keeps the text),
but it must be a conscious behaviour, mentioned in the panel's copy rather than discovered.

**Acceptance criteria:**
- [ ] The `processed` view shows a collapsed panel below the AI-costs line containing the stored
      response; the re-parse control is inside it and not reachable while collapsed.
- [ ] Submitting the panel re-decodes the submitted text and re-seeds the receipt's lines from it.
- [ ] No API call is made, and the receipt's token counts and `parse_cost` are unchanged afterwards.
- [ ] A tag named in the response that did not exist at analysis time but exists now is attached to
      its line after a re-seed — the reported case.
- [ ] Re-seeding replaces the previous draft lines; no stale line or line tag survives.
- [ ] The panel warns that re-seeding discards manual edits to the lines.
- [ ] A `committed` receipt offers no such panel and the endpoint refuses it.
- [ ] Undecodable edited text lands the receipt in `failed` with the edited text preserved, from
      which the existing `failed` affordance can still repair it.
- [ ] The `failed` view's existing behaviour is unchanged.
- [ ] `./gradlew check` is fully green, with no tool weakened and no suppression added.

**Out of scope:**
- Re-running the model (edited AI note, fixed crop) — that is `receipt-processing/18`.
- Creating tags from the AI response at seeding time — explicitly rejected above.
- Surfacing unresolved tag chips in the post-process editor — related, separate, see below.
- Bulk re-seed across selected receipts — see below.

## Follow-ups this does not cover

**The silent drop is the root cause and is still unaddressed.** With this feature the damage is
repairable, but nothing tells the operator it happened — the tag echo is dropped with no warning, no
line marker, and no log. That is how a whole vacation's tagging was lost unnoticed. Worth its own
ticket: show an unresolved chip on the line in the post-process editor, with a one-click create
(which keeps creation operator-controlled rather than model-controlled).

**Bulk.** The panel is per receipt, so clearing the ~50-receipt backlog that prompted this means
opening 50 receipts. The receipts list already has the multi-select used for batch analysis; a
"re-seed selected" action over the same selection would reuse `reparse` unchanged (passing each
receipt's stored `parse_raw` untouched). Not filed yet — raise if the manual pass proves tedious.
