# Confirming a zero-amount receipt fails with "Something went wrong"

Status: ready-for-agent
Category: bug
Severity: medium
Area: Receipts — Confirm / commit path (`ReceiptSplitEntries` → `DockSplitService`)

Found 2026-09-08 by the owner. A parking ticket was scanned that carries no price — only the
date/time and the parking operator's name. The intent was to book a **placeholder zero
transaction** now (payee + date, amount 0), then reconcile and correct the amount when the charge
shows up on the bank statement. Confirm fails.

## Symptom

`POST /receipts/189/confirm` returns the generic htmx error ("Something went wrong"). Server log:

```
ERROR ... v.hauptbuch.web.GlobalHtmxErrorAdvice : Unhandled exception during htmx request POST /receipts/189/confirm
java.lang.IllegalArgumentException: A split needs at least one line
    at volkovandr.hauptbuch.operations.DockSplitService.commit(DockSplitService.java:97)
    at volkovandr.hauptbuch.receipts.ReceiptCommitService.confirm(ReceiptCommitService.java:86)
    at volkovandr.hauptbuch.receipts.ReceiptProcessingController.confirm(ReceiptProcessingController.java:445)
```

## Repro

1. Scan / create a receipt, get it to `processed`.
2. In the editor: pick a date, pick a paying account, set **Total = `0,00`**, add **one line** with
   a category (e.g. `Parking`) and **amount `0,00`** (blank amount behaves the same).
3. Confirm.

Result: error page, receipt stays `processed`, nothing booked.

## Root cause

The Confirm gate and the commit path disagree about whether an all-zero receipt is bookable.

- **`ReceiptConfirmGate` lets it through.** `ReceiptEditorAssembler.status(hasTotal, balanced)`
  returns `STATUS_BALANCED` because the total field is non-blank (`hasTotal = true`) and
  `remaining = 0 − 0 = 0` (`balanced = true`). `checkTotal` only blocks `STATUS_NO_TOTAL` and
  non-balanced. `checkLines` sees a non-empty line pointing at a postable category. No finding →
  Confirm proceeds.
- **`ReceiptSplitEntries.of` then empties the entry.** `mergedLines(...)` ends with
  `.filter(ReceiptSplitEntries::isNonZero)` (added for issue 15 — drop a group whose lines net to
  zero, e.g. an item fully cancelled by its own storno). With every line at zero, **every** group
  is dropped, so `booked` is `[]`.
- **`DockSplitService.commit` rejects that** at line 96–98:
  `if (entry.lines().isEmpty()) throw new IllegalArgumentException("A split needs at least one line")`.

Note the tension with `DockSplitService`'s own class Javadoc, which explicitly says a net-zero
receipt is legal: *"an exactly zero sum booked on the debit side — a net-zero receipt is legal and
recordable"*. That refers to lines that individually carry amounts but **net** to zero (an expense
line and an equal income line), which still produce category legs. A receipt whose lines are each
literally zero produces no legs at all, and the empty-check fires.

## Not covered by tests

`ReceiptSplitEntries` / `ReceiptConfirmGate` unit tests do not exercise an all-zero receipt.
Whatever the fix, add that case to both.

## Agent Brief

**Category:** bug
**Summary:** An all-zero receipt throws instead of booking. Book it as a `pending_review`
transaction — giving that already-built, never-produced lifecycle value its first producer — rather
than refusing it or asserting a zero as fact.

**Current behavior:**

As traced above: `ReceiptConfirmGate` passes an all-zero receipt (total `0,00`, lines summing to
`0,00` → `STATUS_BALANCED`), `ReceiptSplitEntries.mergedLines`' `.filter(isNonZero)` then drops
every group leaving `booked = []`, and `DockSplitService.commit` refuses an empty line list. The
owner sees "Something went wrong".

Two facts that shaped the decision:

- **`lifecycle = 'pending_review'` is fully built and has no producer.** It is in `V1__core_schema`'s
  check constraint; `RegisterRowRenderer:77` already renders those rows muted and dashed with **no
  running balance** (§2.10); `register.css:215` already styles them. Nothing in the app ever writes
  the value. It is shaped exactly like the placeholder the owner wanted.
- **The engine is of two minds about zero.** `LedgerService.validatedSingleCurrency` accepts an
  all-zero transaction (0 sums to 0); `validatedCrossCurrency` *explicitly* refuses one — "values
  the whole transaction at nothing". Single-currency acceptance becomes load-bearing here.

**Desired behavior:**

1. **Keep the zero line.** Suppress `mergedLines`' zero-drop only when it would empty the entry, so
   the booking is a normal two-leg transaction (`Cash 0,00 / Parking 0,00`) that later edits into
   `Cash −5 / Parking +5`. A storno pair that nets to zero *within* a receipt that still books other
   lines is still dropped — issue 15's behaviour is preserved.
2. **Lifecycle is chosen at book time by "is the entry all-zero".** Receipt Confirm books
   `pending_review` when every line nets to zero, `confirmed` otherwise. This also makes re-entry
   (Confirm on a reopened receipt that now carries real amounts) do the right thing with no extra
   rule.
3. **The receipt reaches `committed`** either way — it points at a real transaction. The
   "unfinished" signal lives on the muted register row, not in the receipt worklist.
4. **Promotion is implicit and one-way.** A dock/split edit that saves a **non-zero** amount
   promotes `pending_review` → `confirmed`. An edit that saves it still zero (fixing the payee or
   date while the amount is unknown) leaves it `pending_review`. A `confirmed` transaction edited
   down to zero **stays** `confirmed` — never auto-demoted.
5. **Cross-currency stays refused, with a better message.** `ReceiptConfirmGate.checkCurrency`
   already blocks a cross-currency receipt with a zero funding total. Keep the block — parking a
   conversion whose rate is unknown records nothing, and the engine refuses an all-zero-base
   transaction independently — but reword it to say that parking is not available for a
   foreign-currency receipt, so the asymmetry (a EUR ticket parks, a CHF one does not) reads as
   deliberate rather than a bug.
6. **No new UI.** No lifecycle indicator, no state control, no "park this" affordance in the dock.
   The receipt path is the only producer. Revisit when there is a second use case.

**Key interfaces:**

- `ReceiptSplitEntries.mergedLines` / `isNonZero` — the zero-drop suppression (point 1).
- `TransactionDraft` — add a `pendingReview(...)` factory beside `confirmed(...)`; the record
  already carries `lifecycle`.
- `DockSplitService.commit` / `SplitEntry` — must be able to carry a lifecycle rather than always
  building `TransactionDraft.confirmed(...)`.
- **`TransactionRepository.updateHeader` already writes `lifecycle` on edit, and every edit path
  hardcodes `TransactionDraft.confirmed(...)`** — so today *any* edit would promote, including one
  that saves zero. Point 4's non-zero condition must therefore be **added**, not inherited from
  existing behaviour. This is the one place the implementation is easy to get subtly wrong.
- `ReceiptConfirmGate.checkCurrency` — reword only (point 5).
- `RegisterRowRenderer` — no change; pin the muted/dashed/no-balance rendering with a test, since
  this issue makes it reachable for the first time.
- `LedgerService.validatedSingleCurrency` — no change; add a test pinning that an all-zero
  single-currency transaction is accepted, as that is now relied upon.

**Acceptance criteria:**

- [ ] Confirming a same-currency receipt whose lines all net to zero books a two-leg transaction
      with both amounts `0,00` and lifecycle `pending_review`; the receipt becomes `committed`.
- [ ] That row renders in the register muted, dashed, with no running balance, carrying its date,
      payee and receipt paperclip.
- [ ] Editing that transaction to a non-zero amount and saving promotes it to `confirmed`.
- [ ] Editing it while it is still zero leaves it `pending_review`.
- [ ] A `confirmed` transaction edited down to zero stays `confirmed`.
- [ ] A receipt with a storno pair netting to zero in one category group, alongside other lines,
      still drops that group and books `confirmed` (issue 15 unchanged).
- [ ] A cross-currency receipt with no amount is still refused, with the reworded message.
- [ ] No lifecycle UI is added anywhere.
- [ ] `./gradlew check` green. Tiers per §6: the zero-drop suppression, the lifecycle choice and the
      promotion rule are decision logic → **unit**; the confirm→register round trip and the muted
      row rendering → **integrationTest**.

**Out of scope:**

- A first-class "amount unknown" receipt state, or any reconciliation workflow — bank statement
  reconciliation is an unbuilt backlog item and will define its own matching.
- A general "park this" affordance in the entry dock.
- Making `pending_review` reachable from anywhere else (the recurring module will define its own
  producer when it lands).
