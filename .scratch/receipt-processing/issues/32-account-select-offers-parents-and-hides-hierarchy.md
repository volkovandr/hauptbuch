# The receipt screen's Account select offers parent accounts and shows no hierarchy

Status: resolved
Category: bug
Severity: medium
Area: Receipts — processing screen, paying-account `<select>` (`receipt-process.html` `#receipt-account`, fed by `RegisterService.accountOptions` via `register.accounts()`)

Reported by the owner 2026-09-26:

> In the receipt interface, after AI processing, the account picker shows all accounts, parent and
> leaves all together. And if I select a parent, it does not work (obviously). I would like parents
> not to be shown in the dropdown, and the leaves appear as "<Parent name> - <Leaf name>" (full
> hierarchy, dash-separated).

## The problem

The paying-account `<select>` renders `register.accounts()`, the register's post-to set:
`RegisterService.pickable(openOwnAccounts())` mapped by `accountOptions`. That set drops closed
accounts and per-person leaves, but applies **no posting-leaf filter**. Each option's text is
`entryValue()`, which is the bare `Name (CUR)`. So:

1. **Parents are offered.** A parent account (one with real children) can be selected. It gets
   through as a real `accountId` and is only refused later, when the funding leg meets the
   leaves-only rule (data-model §5). To the operator that looks like a broken Confirm.
2. **No hierarchy.** The flat list gives no way to tell a parent from a leaf. Two same-named leaves
   under different parents (`BankAaa - Credit card`, `BankBbb - Credit card`) also look identical.

## Expected

- The select offers **posting leaves only** among the open, non-person own accounts.
- Each option shows the full path joined with ` - `, the same idiom the Category picker uses, and
  keeps the currency suffix: `BankAaa - Credit card (EUR)`. A top-level leaf stays `Cash (EUR)`.
- Sorted by that path.
- If a parent id is posted anyway (stale form or hand-crafted request), the editor refuses it with a
  clear inline message. It must not reach commit.

## Notes

- **The root cause is the one in `transaction-register-ui/25`.** That issue covers the register
  dock's Account datalist and transfer targets, and both read from the same
  `RegisterService.accountOptions`. Fixing the option source there fixes this select too, so do the
  two together (plus `people-management/01`, the Settle-up `<select>`: one fix, three callers).
  This surface is simpler than the register's. A `<select>` posts an id, not text, so the
  name-resolution and ambiguity problems in register/25 don't apply here. Only the option list
  and its labels do.
- `AccountService.findPostableLeafPaths(types, separator)` already produces leaf-only
  `Parent - Child` paths, but it doesn't filter `closedAt` or `personLeaf`. Combine it with the
  existing `pickable()` filters rather than loosening either (register/25 notes the same).
- If the label change goes through `RegisterAccountOption.entryValue()` / `AccountEntryLabel`,
  check that the register's edit-mode reconstruction still matches (see register/25's notes). If the
  receipt screen needs a path label the register doesn't, add a separate accessor rather than
  forking the format.
