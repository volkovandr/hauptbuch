# Receipts list: let any column be sorted

Status: ready-for-agent
Category: enhancement
Severity: medium
Area: Receipts — register list screen (`receipts.html`/`ReceiptRegisterController`/
`ReceiptRepository.findForRegister`); overlaps the app-wide sorting backlog
(`implementation-plan.md` §14, "Register follow-ons: column re-sorting")

## Request (owner)

The receipts list should be sortable by any of: capture date, transaction date (see issue 09),
payee, amount — both ascending and descending.

## What exists today

Neither list screen in the app supports sorting today — both are fixed-order:

- **Receipts**: `findForRegister` has a hardcoded `order by captured_at desc, receipt_id desc`
  (`ReceiptRepository.java:69`); no sort/order request param exists anywhere in
  `ReceiptRegisterController` or `ReceiptProcessingController`; the list's `<th>` headers
  (`receipts.html:101-113`) are plain text, not links/buttons.
- **Transaction register** (checked as a possible reference pattern): also fixed-order, and
  explicitly deferred — `register.html:16` ("Sorting is deferred (plan §14); order is fixed
  date-ascending") and `RegisterFilter.java:8` say so directly. `RegisterRepository` has only
  hardcoded `order by` clauses.
- `implementation-plan.md:516` lists "column re-sorting with the balance-hide rule (register §2.7)"
  as an unscheduled §14 backlog item — so this receipts-list ask is one slice of a sorting pattern
  the app hasn't designed anywhere yet, not an isolated gap.

There is no existing sortable-column-header implementation in the codebase to reuse as a pattern —
this would be new UI, not a port of something already built.

## Agent Brief

**Category:** enhancement
**Summary:** Make the receipts register list's Captured, Txn date, Merchant, and Total columns
sortable (ascending/descending), query-param-driven, matching the existing `state`/`range` filter
convention.

**Current behavior:**
The receipts list is fixed-order: newest-captured-first, with no way to change it. The list's
column headers are plain text, not controls. This is one column short of the transaction register's
own (still-deferred) sorting need, but the register's sorting is blocked on a harder problem this
list doesn't have — a per-account running-balance column that's only meaningful in date order. This
list has no such column, so it isn't blocked by that.

**Desired behavior:**
Four of the list's columns become sortable via click, independently of the existing `state`/`range`
filters:

- **Captured** and **Total** are plain columns on the receipt row itself — sort these via the same
  query the list already runs (add an `order by`), keeping that query in whichever test tier it's
  in today (a plain filtered select with an order — no join, so the round-trip/integration tier, not
  `sqlLogicTest`).
- **Txn date** and **Merchant** are not raw columns — both are already resolved via a separate
  per-list batched lookup, keyed by receipt id (one lookup returns the linked transaction's booking
  date for committed receipts, absent for everything else; the other resolves the payee name if one
  is assigned, else the parsed merchant text, absent if neither exists). Sort these **in memory**,
  after both lookups are fetched, using the same batched-lookup calls that already back those two
  columns — do not add a join to the list's base query for this. The list is unpaginated, so an
  in-memory sort over the full fetched set is not a performance concern.

**Sort semantics** (apply uniformly across all four columns):
- No `sort` param → today's behavior, unchanged: newest-captured-first.
- A column's first click sorts in that column's natural default: date columns (Captured, Txn date)
  newest-first; Merchant A→Z; Total largest-first. A second click on the same column flips direction.
- Tie-break, every sort: captured date (same direction as the primary sort), then receipt id, as a
  final deterministic tiebreak. (When the primary sort *is* Captured itself, this collapses to
  receipt id as the sole tiebreak.)
- Nulls (Txn date is absent for any receipt without a linked transaction; Merchant is absent when
  neither a payee nor a parsed merchant name exists): standard per-direction placement — sorts last
  in ascending order, first in descending order. Do not special-case nulls to a fixed end regardless
  of direction.

**Key interfaces:**
- The list's GET request gains two optional params, e.g. `sort` (one of the four column keys) and
  `dir` (`asc`/`desc`), read the same way the existing `state`/`range` params are — carried through
  the filter form, the header links, and the background list-refresh poll (the poll re-fetches on a
  timer while a row is `processing`; it must include the active `sort`/`dir` in its request the same
  way it already includes `state`/`range`, so an in-flight sort survives a background refresh rather
  than reverting).
- The four sortable `<th>` header cells become links/buttons that submit a request with the clicked
  column as `sort` and the appropriate `dir` (see semantics above) — this submits immediately, it
  does not stage behind the existing "Apply" button (which stays scoped to `state`/`range` only).
  Each such link must itself carry the *current* `state`/`range` values forward, since it's a
  separate request from the filter form's own submit.
- The currently-active sort column's header shows a plain-text directional glyph (↑ ascending, ↓
  descending) alongside its label; the other three sortable headers show no glyph, just their label
  as a plain clickable control. The five non-sortable columns (Scan, State, Account, transaction
  link, status) are unchanged plain `<th>` text.
- Shape this generically (a `sort`/`dir` query-param convention, and a header-link markup pattern
  that isn't receipt-specific) so it's a natural fit for the transaction register to adopt later for
  its own non-balance columns — but do not attempt to build or wire anything into the register as
  part of this ticket.

**Acceptance criteria:**
- [ ] With no `sort`/`dir` param, the list renders exactly as it does today (newest-captured-first).
- [ ] Each of Captured, Txn date, Merchant, Total can be sorted ascending and descending via its
      header.
- [ ] Each column's first click produces that column's documented natural-default direction; a
      second click on the same column flips it.
- [ ] Ties within a sort break by captured date (same direction), then receipt id.
- [ ] A receipt with no linked transaction sorts last under Txn-date-ascending and first under
      Txn-date-descending (and likewise for a receipt with no resolvable Merchant, under Merchant
      sorting).
- [ ] The active sort survives: switching `state`/`range` and pressing Apply, and a background
      list-refresh triggered by the processing poll — neither reverts the list to the default order.
- [ ] The active column's header shows the correct directional glyph; the other three sortable
      headers show none.
- [ ] Existing `state`/`range` filtering and the existing Apply-button flow are unaffected by any of
      the above.

**Out of scope:**
- Any change to the transaction register's own (still-deferred) sorting — this ticket touches the
  receipts list only.
- Pagination, or any performance work beyond the in-memory sort described above.
- Sorting by any column other than the four named here (Scan, State, Account, transaction link, and
  status stay unsorted).
- A formal shared-component extraction for the header-link pattern — build it generically, but don't
  invest in generalizing it beyond what receipts itself needs.
