# Receipt commit should create one posting per category (summed), not one per line item

Status: ready-for-agent
Category: enhancement
Severity: medium
Area: Receipts — commit posting generation (`ReceiptSplitEntries`, `DockSplitService`) × register
display (`RegisterRowRenderer`)

Sourced from `docs/potential-feature-ideas.md` ("Receipts page" section, added 2026-08-18) after
first real-conditions use: "When entering a transaction into the register from a receipt, the
postings should not be created per each item in the receipt, but per each category. group by
category, sum over amount. Otherwise it appears weirdly in the register, the categories column
shows something like 'Food, Food, Food +20' instead of just 'Food'."

## What exists today

Confirmed by design, not a bug: today one posting/leg is created per receipt line item, with no
aggregation by category —

- `ReceiptSplitEntries.of`/`lineOf` (`:35-57`, `:59-76`) build one `SplitLineDraft` per
  `WorkingLine`.
- `DockSplitService.sameCurrencyLegs` (`:172-189`, similarly `crossCurrencyLegs` at `:288-328`)
  loops every entry's lines and adds one counter-leg `PostingDraft` per line.
- `RegisterRowRenderer.cellFor` (`:177-188`, `MAX_CATEGORY_CHIPS` at `:38`) renders one chip per
  counterpart leg with a capped `· +n` overflow — this is the display symptom described above, and
  it's a direct consequence of the commit-time behavior, not an independent display bug.

Existing tests: `ReceiptSplitEntriesTest`, `DockSplitServiceTest`, `RegisterRowRendererTest`.

## Open questions before this can be scoped

1. **Scope of "same category."** Category leaves are per-currency by construction
   (data-model §6.5/CLAUDE.md §4), so within one commit all lines routed to `Food-EUR` really are
   the same leaf — grouping should be safe on that front. But: should grouping merge across lines
   that share a category leaf but carry **different tags**, or a **different per-line AI note**? If
   two `Food` lines have different tags, summing them into one posting means one of the two
   line-level tag sets has to win, get unioned, or the merge has to be restricted to lines with
   identical tags.
2. **Person-transfer legs.** Should a category-leg merge also apply to `for <person>`/`by <person>`
   transfer legs that repeat (e.g. two Bobby items on one receipt), or should grouping be scoped to
   plain category legs only, leaving transfer legs one-per-line as today?
3. **Is this purely a commit-time posting change, or does the *register display* also need its own
   independent chip-dedupe fix** (summing what's already-committed postings for display, without
   changing what commit creates)? A display-only fix is far smaller but doesn't reduce the actual
   posting count in the ledger; a commit-time change is the "real" fix the request describes but
   changes the ledger's audit trail (splitting a committed transaction back into original receipt
   line amounts becomes lossy — the per-item detail only survives on the `receipt`/line-item
   records, not in the postings).
4. Does this apply to the receipt-commit path only, or should the same grouping apply to a manually
   entered split transaction in the register dock (`DockSplitService` is shared by both callers per
   the code above)?

## Agent Brief

**Category:** enhancement
**Summary:** Receipt lines that resolve to the same posting identity should be summed into one
posting at commit time, instead of the ledger receiving one posting per receipt line item.

**Current behavior:**
Confirming a receipt builds one split-line draft per receipt line item, unconditionally, and hands
the full list to the shared split-commit service, which books exactly one counter-leg posting per
draft it receives. A receipt with several line items in the same category (the common case — e.g.
three grocery items) therefore books three separate postings rather than one, and the register's
Category cell — which renders one chip per counterpart leg, capped with a "+n" overflow — displays
this as visible clutter (e.g. "Food, Food, Food +20") for what a human would expect to read as a
single category entry. This is confirmed by reading the current line-building and leg-building
code, not assumed from the bug report.

**Desired behavior:**
Before a confirmed receipt's lines are handed to the shared split-commit path, lines that are
identical on every field that would otherwise land on a distinct posting are combined into one
draft carrying the summed amount. Two lines combine if and only if they match on **all** of: the
resolved category leaf (or the transfer-target account, for a transfer line), the transfer
direction, the attributed person's name, the person direction, the person-revival choice, the tag
set (order-independent), and the line note (including the case where both are blank). Differ on
any single one of those and the lines must stay on separate postings — a line carrying its own tag
or note is never folded into another line's posting, even if they'd otherwise share a category,
since that annotation is operator-entered detail that summing would otherwise silently discard.

This rule applies uniformly across line flavors — plain category lines, transfer-to-own-account
lines, and person (`for`/`by`) lines all combine under the identical rule; there is no
category-only special case. The combined amount is the sum of the group's *signed* contributions
(the existing typed/storno-aware sign convention already used to compute the funding total), so a
storno line combines correctly with a non-storno line in the same group rather than having its
magnitude summed blindly.

The shared split-commit service used by both receipt confirm and the register's own manual
split-transaction entry screen must **not** change — it should keep booking exactly one posting per
draft it is given, unchanged. The combining happens only on the receipt-confirm path, before that
service is called; a manually-typed split transaction in the register keeps booking one posting per
typed line, with no combining, regardless of how many lines share a category.

**Key interfaces:**
- The receipts-module type that turns a confirmed receipt's lines into the shared split-entry shape
  is where the merge belongs — it should group and sum lines before building the final draft list.
  The shared split-commit service itself takes no change.
- The per-line draft type already carries every field the merge key is built from (the resolved
  category/transfer/person identity, direction, revive choice, tags, and note) plus the typed
  amount string as a separate field — group on everything except the amount, then combine each
  group into one draft whose amount is the summed signed contribution.
- Reuse the existing signed-contribution / amount-formatting logic that already converts a typed
  German amount (with optional storno sign) to a signed value and back for the funding-total math,
  rather than introducing a second parse/format path for the merged sums.

**Acceptance criteria:**
- [ ] Confirming a receipt with several line items that share one category leaf and carry no
      per-line tags or note produces a single posting for that category, whose amount equals the
      sum of those lines' signed contributions.
- [ ] A line carrying its own tag(s) and/or its own note is never combined with any other line,
      even one sharing its category — it always keeps its own separate posting.
- [ ] Two lines sharing a category but differing in note, or in tag set, remain on separate
      postings.
- [ ] The same combining rule applies to repeated transfer lines (same target account, same
      direction) and repeated person lines (same person, same direction, same revive choice) — not
      only to plain category lines.
- [ ] A storno line (a negative typed amount) combines correctly with a non-storno line in the same
      group — the net signed sum is booked, not the sum of magnitudes.
- [ ] Every transaction the fix produces still sums to zero (receipt confirm only ever produces
      single-currency splits today, so no cross-currency case needs to be handled).
- [ ] Manually entering a split transaction directly in the register (not via receipt confirm)
      still books exactly one posting per typed line — confirmed unchanged by this fix.
- [ ] No code change is needed in the register's Category-cell rendering — it already sums
      correctly off however many postings exist; fewer postings from the commit-time fix should
      produce cleaner chips with no separate display-layer change.

**Out of scope:**
- Any change to the shared split-commit service's own leg-building logic, or to the register's
  manual split-transaction entry path — both keep booking one posting per typed line.
- Any change to the register's Category-cell rendering logic — no independent display-side dedupe
  is needed once the commit-time fix lands.
- Reworking how the receipt's own line-item records are stored or shown on the receipt-review
  screen — per-item detail stays exactly as it is there; only what gets booked to the ledger
  changes.
- Cross-currency receipt commits — out of scope because receipt confirm does not produce them
  today.
