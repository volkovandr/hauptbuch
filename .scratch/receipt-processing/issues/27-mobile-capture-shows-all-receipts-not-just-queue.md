# Mobile capture grid shows every receipt, not just the working queue

Status: ready-for-agent
Category: enhancement
Severity: high
Area: Receipts — mobile capture (`ReceiptCaptureController`, `receipt-capture.html`) ×
`ReceiptService.forMobile`

Found 2026-09-13 by the owner in production. With 250+ receipts accumulated, the mobile capture
page (`/receipts/capture`) is noticeably slow, and the owner has silently lost at least one upload:
after shooting a photo, the page redirects and re-renders the (huge) grid; if the owner takes the
next photo before that re-render finishes, the new upload is lost without any visible error.

## Current behavior

`ReceiptCaptureController.capture()` / `.upload()` both call `ReceiptService.forMobile()`
(`ReceiptService.java:190`), which has no state filter at all:

```java
public List<Receipt> forMobile() {
  OffsetDateTime since = OffsetDateTime.now(ZoneOffset.UTC).minusDays(MOBILE_WINDOW_DAYS);
  return receiptRepository.findForMobile(since);
}
```

`findForMobile` (`ReceiptRepository.java:121`) selects every non-deleted receipt captured in the
last `MOBILE_WINDOW_DAYS` (90, hardcoded) regardless of `state` — `committed` receipts included.
`receipt-capture.html` renders the whole result as one `<img>`-per-tile grid with no pagination and
no filter control; there is no `state`/`range` query param on `/receipts/capture` at all (contrast
the PC register, which already has `ReceiptFilters.STATE_QUEUE`/`STATE_ALL`/`STATE_VOIDED` and
`RANGE_90D`/`RANGE_1Y`/`RANGE_ALL`, threaded through `ReceiptRegisterController`).

So every receipt ever committed in the last 90 days — the overwhelming majority once the book is a
few months old — loads and renders on the phone on every visit, and again after every single
upload's PRG redirect.

## Owner decision (2026-09-13)

Ship the simpler of the two proposed shapes now: **working-queue only, no filter UI.** The
full-filter-set option (same `state`/`range` controls as the PC register, defaulting to the
working queue) is split off to [issue 28](28-mobile-capture-filter-controls.md) as a later
enhancement, not part of this fix.

The redirect-before-re-render race (the owner's secondary symptom — an upload silently lost
because the next photo is taken before the PRG re-render finishes) is left unaddressed here: once
the grid is capped to the working queue it will normally be small and fast, which should close the
window in practice. Not otherwise fixed in this issue; reopen or file separately if it still
reproduces afterward.

## Agent Brief

**Category:** enhancement
**Summary:** Mobile capture (`/receipts/capture`) should show only the working queue (everything
except `committed`), not every receipt ever captured in the 90-day window.

**Current behavior:** As traced above — `forMobile()` / `findForMobile` have no state filter at
all, so a `committed` receipt from months ago renders in the grid exactly like a fresh `new` scan.

**Desired behavior:** The mobile grid's query narrows to the same work-queue state set the PC
register defaults to (`ReceiptState.WORK_QUEUE`: `new`, `pre_processed`, `processing`, `processed`,
`failed`). No state/range filter UI is added on mobile in this stage — that is issue 28. The
90-day capture window is unchanged (an orthogonal axis). A receipt that leaves the queue (i.e. is
committed) simply stops appearing in the grid on the next load/poll, the same way it already
disappears from the PC register's default `queue` view today.

**Key interfaces:**
- The mobile grid's read path (today `ReceiptService.forMobile()`): narrow the returned set to the
  work-queue states rather than every state.
- The mobile grid's backing query (today `ReceiptRepository.findForMobile`): add a states
  predicate, reusing the same `state in (...)` shape the register's own repository query already
  uses — don't invent a second query idiom for the same filter (CLAUDE.md §0).
- No new request parameters, controller signature, or template changes are needed — there is
  still no filter to expose in this stage.

**Acceptance criteria:**
- [x] With 250+ historical receipts on record, most `committed`, `/receipts/capture` shows only
      `new`/`pre_processed`/`processing`/`processed`/`failed` receipts captured in the last 90
      days.
- [x] A receipt committed elsewhere (e.g. from the PC register) mid-session drops out of the
      mobile grid on the next load, mirroring the PC register's own default-queue behavior.
- [x] A `new` receipt just captured from the phone still appears immediately after its upload's
      PRG round trip.
- [x] `upload()` and `deleteFromPhone()` are unaffected — they act on a specific id regardless of
      how the grid is filtered.
- [x] Unit tier covers the narrowed state set (repository mocked); the query's own change is a
      plain `where ... state in (...)` predicate — a round-trip case in the integration tier, not
      `sqlLogicTest` (no aggregation, window function, or CTE involved).
- [x] `./gradlew check` green.

**Out of scope:**
- Any filter UI, `state`/`range` params, or a way to reach `committed`/`voided`/older receipts
  from the phone — tracked separately in issue 28.
- The redirect-before-re-render upload race (see "Owner decision" above).
- Changing the 90-day capture window itself.
