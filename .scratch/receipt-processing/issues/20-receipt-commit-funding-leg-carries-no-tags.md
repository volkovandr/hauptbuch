# A committed receipt's tags never reach the paying account's posting, so the register shows none

> *This was generated by AI during triage.*

Status: resolved
Category: enhancement
Severity: medium
Area: Receipts — confirm/commit (`ReceiptSplitEntries`), register tag display

## Report (owner)

Tags added to receipt items are attached only to the category-side postings, never to the paying
account's. Not wrong as such, but the side effect is that **the tag does not appear in the register
table** — it is visible only after opening the transaction for editing.

From the vacation use case: a receipt whose every item carries `Trips:France-2026`, committed, and
in the register the tag is nowhere to be seen.

## The rule (owner-specified, 2026-08-22)

When a transaction is created from a receipt:

- each receipt item's tags go onto that item's category posting — **unchanged from today**;
- the **intersection** of all the items' tag sets goes onto the paying account's posting.

So tagging every item with the same tag (or set of tags) puts that same tag (or set) on the funding
leg. Where items differ, only what they all share lands there — and nothing lands there if there is
no common tag, or if any item has no tags at all.

## Confirmed cause

`ReceiptSplitEntries.of` builds the register's `SplitEntry` for a confirmed receipt and passes
`List.of()` as the entry's transaction-level tag ids. Its own Javadoc states the current behaviour
outright: *"The line's own tags ride along — receipts have no transaction-level tag field, so
nothing lands on the funding leg."*

The receiving side already does the right thing with a non-empty value: `DockSplitService` applies
the entry's tag ids to the **funding leg only** (`tagged(PostingDraft.of(fundingAccount…),
entry.tagIds())`), while each line's own tags go to that line's posting. So this rule needs the
intersection computed and handed over — the commit path itself needs no change, and there is no
risk of double-tagging a category leg.

## Agent Brief

**Category:** enhancement
**Summary:** Give a receipt-committed transaction's funding leg the intersection of its items' tag
sets, so shared tags are visible in the register.

**Current behavior:**
Confirming a receipt books it through the register's shared split-commit path. Each receipt line's
tags are carried onto that line's posting, but the split entry is constructed with an empty
transaction-level tag list, so the paying account's posting is never tagged. The register's row for
the transaction therefore shows no tags, even when every item on the receipt carries the same one;
the tags surface only when the transaction is opened for editing.

**Desired behavior:**
The funding leg receives the set-intersection of the tag sets of the receipt's booked lines. Given
lines all tagged `A`, the funding leg gets `A`. Given lines tagged `{A,B}`, `{A,B}` and `{A}`, it
gets `{A}`. Given any booked line with no tags, or no tag common to all, it gets none. Per-line tags
are unaffected. A receipt with a single booked line is simply the degenerate case: the funding leg
mirrors that line's tags.

**Key interfaces:**
- The receipt→split-entry mapping (`ReceiptSplitEntries`) — computes the intersection and supplies
  it as the split entry's transaction-level tag ids instead of the current empty list. This is the
  only production change the rule requires.
- `SplitEntry`'s transaction-level tag ids and `DockSplitService`'s funding-leg tagging — used as-is,
  not modified. The commit path already applies these to the funding leg alone.

**Decisions folded in (do not re-litigate):**
- **Intersect over the lines that actually book** — i.e. after the same-identity merge and after
  groups netting to zero are dropped. A line fully cancelled by its own storno books no posting, so
  it must not constrain what the funding leg is tagged with.
- **Every booked line participates**, including transfer and beneficiary (person) lines. They are
  receipt items like any other, and the rule is about what all items share.
- **No retro-fix.** Already-committed receipts keep the postings they have. Re-entering a receipt
  (reopen, then confirm again) books afresh and picks up the new rule, which is the existing
  no-drift-check behaviour, not something to add.

**Acceptance criteria:**
- [x] A receipt whose booked lines all carry the same single tag commits with that tag on the paying
      account's posting, and the tag is visible on the register row without opening the editor.
- [x] A receipt whose lines carry `{A,B}`, `{A,B}`, `{A}` puts exactly `{A}` on the funding leg.
- [x] A receipt with any booked line carrying no tags puts no tags on the funding leg.
- [x] A receipt whose lines share no tag puts no tags on the funding leg.
- [x] Per-line (category-side) tagging is byte-for-byte unchanged in every case above.
- [x] A line that nets to zero and is therefore not booked does not reduce the intersection.
- [x] A single-line receipt puts that line's tags on the funding leg.
- [x] A manually-typed register split is unaffected — this changes the receipt path only.
- [x] `./gradlew check` is fully green, with no tool weakened and no suppression added.

**Out of scope:**
- Adding a transaction-level tag field to the receipt editor. The rule derives the funding leg's
  tags from the lines; it does not introduce a header tag input.
- Changing how the register decides which tags to render on a row.
- Re-tagging receipts already committed.

## Note for whoever builds tag reporting

After this change a shared tag lands on **both** the expense legs and the funding leg of the same
transaction — which is already true for a manually-entered split with header tags, but this makes it
the common case rather than the exception. Any tag-based total must filter to flow legs, or a
tagged transaction will net to zero (or double-count, depending on the direction it sums). This is
the same constraint already recorded for transaction-level tags in the register.

Fixed 2026-08-22 (issue/receipts-20, 6ca87bb): `ReceiptSplitEntries.of` computes the intersection
of the booked lines' tag sets and hands it over as the split entry's transaction-level tag ids
where it passed `List.of()` before. As the brief predicted, that was the only production change —
`DockSplitService` already applies those ids to the funding leg alone, so no category leg is
double-tagged and the shared commit path took no change of its own. A receipt commit now behaves
exactly like a manually-typed register split whose header tags happen to be what its lines share.

The premise was verified rather than assumed: the register row renders `labelsByPosting` for the
row's **own** posting, which for a receipt spend is the paying-account leg — which is precisely why
line-only tags never showed. The integration test asserts both the `posting_tag` rows and the
rendered row chip (`#Trips:France-2026`); the chip's `#` is what makes that assertion specific,
since the bare label also appears in the tag datalist on every register page.

`/code-review` found no correctness bugs, and confirmed the two subtle decisions landed: the
intersection runs after the same-identity merge and the zero-drop, and transfer/person lines
participate. It checked the things that could have gone wrong and did not — no `posting_tag`
unique-constraint risk (the funding account can never collide with a category leaf, and the tag
application de-duplicates), no NPE path (neither `SplitLineDraft.tagIds()` nor `WorkingLine.tags()`
is ever null), and no read-back of a committed transaction's postings that could turn the newly
tagged funding leg into a phantom line on Re-enter.

One thing worth recording for whoever builds tag reporting, beyond the note already in this ticket:
`DockSplitService` puts transaction-level tags on the **funding leg only** — the "one `posting_tag`
row per leg" expansion is the *non-split* dock commit's behaviour, not the split path's. Both now
routinely put the same tag on a flow leg and the funding leg, so the flow-leg filter that note
calls for is required, not optional.

`./gradlew check` is green.
