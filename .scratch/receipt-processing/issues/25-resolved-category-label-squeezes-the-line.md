# Category resolution: confirm an inline create before it happens, and move the line's status out of the flex row

> *This was generated by AI during triage.*

Status: ready-for-agent
Category: bug
Severity: medium
Area: `categories` — the shared `/categories/resolve` endpoint and `CategoryService`'s resolution;
the `categoryResolved` fragment; the shared line editor used by **both** the register split panel
and the receipts post-process editor; the register's simple entry dock.

Filed 2026-08-29 from the owner's report, promoted out of `docs/potential-feature-ideas.md` (where
it read as generic content-driven field resizing — the actual trigger is the resolved-category
label). Triaged and grilled the same day; **`transaction-register-ui/14` was folded into this
ticket** during that session, because the two turned out to be the same control at two different
moments. See *Comments*.

## Symptom (owner report)

On a line whose category was preselected by the AI, changing it to a different category makes the
new category's name appear **twice**: in the picker input (correct), and again as a small grey
label at the **far right end of the same row**. Every other element in that row — Item, Category,
Note, Tags — narrows to make room, so the row visibly reflows on every pick.

## Why the row narrows — confirmed by code path

`.split-line` is a flex row whose last item is the resolve target, `<span
class="split-line__resolved">`. Its CSS states the assumption outright — *"The resolved hidden
id/type carrier takes no visual space"*, `flex: 0 0 0`.

That holds only while the slot contains `<input type="hidden">`. `resolveCategoryText` sets
`categoryName` on **every** successful resolve, and the `categoryResolved` fragment renders it
unconditionally as a visible `<span class="entry-dock__resolved muted">`. A flex item defaults to
`min-width: auto`, so it cannot shrink below min-content — the visible text defeats `flex-basis:
0` and the slot claims real width. `.split-line .field` sets `min-width: 0`; that slot does not.

The same slot also hosts the resolve **error** text and the person **Restore/Create-new** revival
buttons, which squeeze the row identically.

The simple entry dock is unaffected: there the fragment lands in `.entry-dock__status`, a
dedicated status line under the fields with a reserved `min-height` — *"out of the fields' flow so
it never disturbs their alignment"*. That is the pattern this ticket generalises to the line row.

The row already renders one thing correctly below the picker: the AI ghost, `<p
class="split-line__ghost muted">AI said: …</p>`, sits inside the category field under the input, so
it costs the row no horizontal space.

## Why `transaction-register-ui/14` folded in here

`14` asked for a confirmation step before an inline category create, so a typo can't silently
create a category. It is the same mechanism and the same UI element as this ticket:

- **One mechanism.** `CategoryService.resolveCategory` has exactly one caller —
  `CategoriesController`'s resolve endpoint — and every category picker in the app posts there: the
  register's simple dock, the register split's lines, and the receipts editor's lines (the latter
  two share one line fragment). Typing `Food - Sweets` runs the identical path on every surface.
- **Creation happens at resolve time**, on the field's `change` event, not at Save/commit —
  `resolveCategory` falls through to `createLeafFromParentChild`. So a "new category: …" label is a
  *post-hoc notice of something already created*, while `14` wants the notice *before*. Build the
  label alone and `14` rebuilds it.
- **The precedent already exists in the same slot.** Person resolution never resolves a
  soft-deleted match silently: it returns a `Pending` outcome and renders a Restore/Create-new pair
  that re-posts with `personDecision`. Category creation wants the same shape.

## Decisions taken (owner, 2026-08-29)

1. **Propose, then confirm.** An unknown category name resolves to a *pending* outcome, not a new
   leaf. The status area shows what would be created and offers an explicit Create.
2. **Everything moves below the picker.** One per-line status area under the category input hosts
   the AI ghost, the error text, the create-confirm, and the person revival choice. The hidden-input
   carrier goes back to being exactly that, so its "takes no visual space" claim becomes true again.
3. **Both surfaces.** One shared fragment, one behaviour — the register split and the receipts
   editor both get it. (Receipts-only would have meant threading a per-surface flag through shared
   markup, i.e. more work for a second way to do the same thing.)
4. **The literal-dash case is not solved here.** `Food - Milk` continues to mean *Milk under Food*.
   The confirm makes that reading visible, which was `14`'s real complaint; anyone wanting a
   top-level category literally named `Food - Milk` uses the Categories screen, which takes name and
   parent as separate fields. No escape syntax is introduced.

## Agent Brief

**Category:** bug
**Summary:** Category resolution must propose an inline create and wait for an explicit decision
instead of creating silently, and a resolved line's status must render under the category picker
instead of at the end of the flex row, where it steals width from every other field.

**Current behavior:**
Resolving a category name creates a new leaf as a side effect of the field's `change` event when
the text matches nothing and parses as `Parent - Child`. Every successful resolve — matched or
created, indistinguishably — returns a caption that the resolve fragment renders as a visible
element inside the line's hidden-input carrier. That carrier is the last item of the line's flex
row and is styled to occupy no space, an assumption only valid for hidden inputs; a visible child
floors it at its min-content width and the row's flexible fields shrink to compensate. The error
text and the person revival buttons render in the same place with the same effect.

**Desired behavior:**
Resolving category text yields one of three outcomes, mirroring the person resolver's existing
sealed-interface shape:

- **Matched an existing leaf** — the id is filled in and **no caption is rendered at all**. The
  picker input already shows what was picked; a confirmation label is not wanted.
- **Would create a new leaf** — nothing is created yet. No id is filled in, so the line cannot
  commit. The status area names exactly what will be created (the child name and its parent) and
  offers a Create control that re-posts the same text with a decision parameter, mirroring the
  person revival buttons' `personDecision`. Only that decision post creates the leaf; it then
  resolves as normal and the status area reports the creation (e.g. `new category: Milk`).
- **Refused** — the existing error cases (unknown bare name, ambiguous path, a non-leaf group) keep
  their messages.

A line's status — AI ghost, error, create-confirm, person revival choice — renders in one status
area beneath the category input, inside the category field, never as a sibling of the row's fields.
The hidden-input carrier contains only hidden inputs. Picking a category, creating one, hitting an
error, or resolving a person must not change the width of any field in the row.

The register's simple entry dock keeps its existing status line; it shares the endpoint, so its
create-confirm must work there too.

**Key interfaces:**

- `CategoryService.resolveCategory(String)` currently returns a bare `long` and creates as a side
  effect. It must instead report which outcome occurred and must not create without an explicit
  decision — so it needs the decision passed in, and a richer return. **`CategoryService` sits at
  PMD's `GodClass` ceiling: adding a public method fails `pmdMain`.** Change this method's signature
  and return type rather than adding a second entry point.
- A `CategoryResolution` type in the `categories` module, modelled on the existing
  `PersonResolution` sealed interface (`Resolved` / `Pending` / `Refused`). Keep the naming and
  record shape parallel — a second idiom for the same concept is what the project rules forbid.
- The resolve endpoint gains a category-decision request parameter alongside the existing
  `personDecision`, round-tripped through the fragment's buttons the same way the person decision
  is (including the per-line `index` and the caller's field names, so a split line's decision
  resolves that line).
- The `categoryResolved` fragment: emit no caption for a plain match; emit the create-confirm and
  the created-notice for the create path; keep the error and person-revival branches. Whatever the
  revival buttons target must follow the status area to its new location.
- The line row's CSS: the hidden-input carrier's "no visual space" rule becomes safe again; the new
  status area must not participate in the row's horizontal flex sizing.

**Acceptance criteria:**

- [ ] Resolving text that matches an existing leaf fills the hidden id and renders no caption.
- [ ] Resolving `Parent - Child` where `Child` does not exist creates **nothing**, leaves the
      hidden id empty, and renders a confirm naming the child and the parent.
- [ ] Re-posting that text with the create decision creates the leaf, fills the hidden id, and
      reports the creation.
- [ ] A line left at the unconfirmed-create stage cannot commit — it fails validation the same way
      any unresolved category does.
- [ ] The existing refusal messages (unknown bare name, ambiguous path, non-leaf group) are
      unchanged.
- [ ] The person Restore/Create-new flow still resolves the correct line and still commits.
- [ ] The resolve response's visible output never lands in the row's hidden-input carrier; that
      carrier's rendered content is hidden inputs only, on every branch.
- [ ] Verified **in a browser** on both the receipts post-process editor and the register split
      panel: picking a category, confirming a create, triggering an error, and resolving a person
      leave every field in the row at the same width. (A MockMvc content assertion cannot show
      this — it proves only what was emitted.)
- [ ] The register's simple entry dock resolves, confirms a create, and commits as before.
- [ ] Test tiers per the project rules: the resolution decisions unit-tested with the repositories
      mocked; the endpoint's rendered fragment asserted in the integration tier, where the existing
      register entry/split screen tests already post to this endpoint and are the pattern to follow.
- [ ] `./gradlew check` fully green, with no tool weakened and no new coverage exclusion.

**Out of scope:**

- Creating a top-level category whose literal name contains the path separator (decision 4 above) —
  no escape syntax, no second button for the top-level reading.
- The AI seeder's own category matching at analyse time. It resolves through the AI-vocabulary
  term lookup, which is explicitly non-creating, and is unaffected by this change.
- The account, payee, and tag pickers, and the tag chip resolve endpoint.
- The tags block's corner/size inconsistency (`transaction-register-ui/19`) — a separate styling
  ticket on the same row.
- Any change to what a *committed* line does with the resolved id (the receipts draft's deferral of
  the per-currency leaf to Confirm stays exactly as it is).
