# Manually resolving a cross-currency park does not discard the ledger-duplicate-scan snapshot

Status: needs-triage
Category: bug
Severity: medium (latent until f2 — a false-green commit gate over an un-scanned bookable row)

Area: Import — cross-currency park resolution vs. the f1 duplicate-scan gate (`ImportCrossCurrencyParkService`, `ImportMirrorMatchingService`, `ImportDuplicateScanRepository`)

## What happens

f1 (import.md §9, Q-IMP-5) makes the ledger duplicate scan a re-runnable snapshot that the commit
gate treats as **discarded** on any importer-side change that could move which staged rows overlap
the live ledger. `ImportMirrorMatchingService` names the three such changes in its own class
javadoc — *"a file staged/removed, an account mapping edited, or **a cross-currency park
resolved**"* — and clears the snapshot (`ImportDuplicateScanRepository.clearScan`) for all of them
by routing through `rematchCurrentSession()`. `ImportCategoryMapService` clears it directly for the
one path that doesn't pass through there.

But the **manual** park-resolution paths bypass all of that. `ImportCrossCurrencyParkService`:

- `manualMatch(importPostingId, mirrorPostingId)` and
- `closeParkWithFarAmount(importPostingId, farAmount)`

call `ImportMirrorRepository` directly and then only
`rateWriteBackService.writeBackObservedRates(sessionId)`. They never call
`rematchCurrentSession()` and the service has no `ImportDuplicateScanRepository` dependency at all,
so `clearScan` is never invoked.

A staged transaction that was `parked` is **out of scope** for the scan — `MATCH_QUERY` filters
`t.state = 'ready'`. When the owner resolves the park by hand, the surviving sighting flips to
`ready` (`setTransactionState(survivor, READY)` inside the repo mutation) and is now newly
bookable and newly in scope for the scan. But:

- the snapshot is **not discarded** (no `clearScan` on this path), and
- the snapshot is **not stale** — `staleAgainstActivity` only compares `ran_at` against
  `max(transaction.updated_at)`, and park resolution touches only `import_*` tables.

So `ImportDuplicateScan.cleared()` stays `true` and `ImportReview.commitReady()` reports the
campaign ready to commit — with a freshly-bookable transaction that the scan never examined. At f2
that row books without ever having been checked against the live ledger for a duplicate.

Automatic park resolution is fine: it runs inside `rematch()` via `rematchCurrentSession()`, which
clears the snapshot. Only the two manual paths are affected.

## Where to fix

Give the manual paths the same discard the automatic path gets. Either:

- inject `ImportDuplicateScanRepository` into `ImportCrossCurrencyParkService` and call
  `clearScan(sessionId)` at the end of `manualMatch` / `closeParkWithFarAmount` (mirrors
  `ImportCategoryMapService`'s direct call), or
- route both through `ImportMirrorMatchingService.rematchCurrentSession()` after the mutation (a
  rematch is cheap and idempotent, and re-running it after a manual resolution is harmless) — this
  also keeps the "all importer-side change discards the snapshot" invariant in one place.

Add the missing coverage to `ImportCrossCurrencyParkServiceTest` (a `verify(...).clearScan(...)`
alongside the existing `writeBackObservedRates` verification), matching
`ImportMirrorMatchingServiceTest`'s existing check for the rematch path.
