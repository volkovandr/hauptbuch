# Rescan re-raise skips a voided ledger transaction, silently dropping the owner's adjudication

Status: needs-triage
Category: bug
Severity: minor (outcome-safe — the staged row books; the lost item is the recorded decision + its audit fingerprint)

Area: Import — ledger duplicate scan reconcile (`ImportDuplicateScanRepository.rescan`, plan f1)

## What happens

`ImportDuplicateScanRepository.rescan` runs two statements after upserting the snapshot:

1. **re-raise** — an adjudication made against a ledger transaction that has changed since the
   decision goes back to `pending`:

   ```sql
   update import_duplicate_match m
      set adjudication = 'pending'
     from transaction lt
    where m.import_duplicate_scan_id = :scanId
      and lt.transaction_id = m.transaction_id
      and lt.deleted_at is null                     -- <-- this filter
      and m.adjudication <> 'pending'
      and (m.ledger_seen_at is null or lt.updated_at > m.ledger_seen_at)
   ```

2. **drop / add** — a no-longer-overlapping pair is removed when it is "safe" to.

The class javadoc states the invariant: *"a pair the owner adjudicated whose ledger transaction has
since been touched … is **re-raised** to `pending` — whether or not it still overlaps — so a stale
decision is never trusted **and never silently lost**."*

Voiding a ledger transaction **is** "touching" it — `TransactionRepository` void stamps
`deleted_at = now(), updated_at = now()`. But the re-raise's `lt.deleted_at is null` clause
excludes exactly that case, so a voided-since-adjudication match is **not** re-raised. It then
falls into the drop CTE: `MATCH_QUERY` also filters `lt.deleted_at is null`, so the pair is not in
`fresh`; and the drop's safety branch
`or not exists (select 1 from transaction lt where … and lt.deleted_at is null)` is now true, so
the match row is **deleted**.

Net effect: the owner's `skip` / `import` decision — and the `ledger_seen_at` fingerprint that
recorded which ledger version it was made against — disappear with no trace on the next rescan,
contradicting the "never silently lost" invariant.

## Severity / blast radius

- **Outcome is safe.** Once the ledger transaction is voided there is genuinely no live duplicate,
  so dropping the match and letting the staged row book at f2 is the correct result.
- What's lost is the **audit trail**: the review no longer shows that this overlap was ever
  considered, and the decision's `ledger_seen_at` is gone.
- The "un-void then re-run" path the reviewer flagged is **not reachable today** — there is no
  restore/undelete method in `TransactionRepository` (only `findVoidedIds`, a read). If a restore
  path is ever added, a restored transaction would re-enter `fresh` and the pair would reappear as
  a plain `pending` with no memory of the earlier decision — the owner re-adjudicates from scratch.

## Where to fix

Decide what a void should mean for an adjudicated match, then make the code and the javadoc agree.
Options:

- **Re-raise on void too** (honour the stated invariant): drop the `lt.deleted_at is null` clause
  from the re-raise `update` (the `lt.transaction_id = m.transaction_id` join already guarantees
  the row exists), and tighten the drop CTE so a re-raised row with a non-null `ledger_seen_at` is
  not immediately deleted for a voided transaction — i.e. a re-raised `pending` match survives one
  cycle so the owner sees "this ledger transaction was voided; your earlier decision no longer
  applies".
- **Accept the drop as intended cleanup** and narrow the javadoc: "re-raised … unless the ledger
  transaction was voided, in which case the match is removed (no live duplicate remains)."

The SQL-logic tier (`ImportDuplicateScanSqlLogicTest` / whatever f1 named it) should gain a crafted
case: adjudicate `skip`, void the ledger transaction, rescan, assert the chosen behaviour.
