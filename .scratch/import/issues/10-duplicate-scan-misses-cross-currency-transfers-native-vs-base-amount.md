# Duplicate scan never matches a cross-currency transfer — staged base amount vs ledger native amount

Status: resolved (owner-confirmed 2026-09-06)
Category: bug
Severity: major (a true duplicate books silently at f2 — the exact "campaign ran for weeks while
Hauptbuch stayed in daily use" scenario the scan exists to catch, defeated for every cross-currency
transfer)

Area: Import — ledger duplicate scan detection (`ImportDuplicateScanRepository.MATCH_QUERY`, plan f1)

## What happens

Owner hand-enters, via the register, a transfer that also exists as a staged import row —
`BankAaa-XXX → BankAaa-EUR`, 11.03.2014, 599 999,64 XXX / 11 707,31 EUR. Runs the duplicate scan on
the review page. **Zero matches.** The staged row will book a second copy at f2.

Reproduced against the live dev DB (session 2):

- staged `import_transaction` 17764, `state = 'ready'`
  - funding leg: `import_posting` 43446 — `BankAaa-EUR`, `amount = 11707.31`, `counter_amount = null`, `funding = t`
  - non-funding leg: `import_posting` 43445 — `BankAaa-XXX`, `amount = -11707.31`, `counter_amount = -599999.64`, `funding = f`
- ledger `transaction` 175, date 2014-03-11, not deleted
  - `posting` 829 — account 118 `BankAaa-EUR`, `amount = 11707.31`, `base_amount = 11707.31`
  - `posting` 828 — account 120 `BankAaa-XXX`, `amount = -599999.64`, `base_amount = -11707.31`
- `import_duplicate_scan` row present (`ran_at` set), `import_duplicate_match` **empty**.

## Root cause

`MATCH_QUERY`'s `staged_leg` CTE takes the non-funding leg amount straight from `import_posting.amount`:

```sql
staged_leg as (
  select p.import_transaction_id,
         coalesce(ic.account_id, ia.account_id) as leg_account_id,
         p.amount                              as leg_amount   -- <-- funding-currency view
  ...
```

For a **cross-currency** transfer leg, `import_posting.amount` is the *funding-currency* view of the
leg (here −11 707,31 EUR) and the real native amount that crossed lives in `counter_amount`
(−599 999,64 XXX) — the convention `ImportMirrorRepository` documents ("the surviving sighting's
transfer leg takes the real far-currency amount as its `counter_amount` (V22), same sign as
`amount`"; f2 reads `amount`/`counter_amount` at booking time).

The ledger stores the mirror image: `posting.amount` is **native** (−599 999,64), `posting.base_amount`
is the base-currency value (−11 707,31).

So the leg `exists` check —

```sql
join posting lleg on lleg.transaction_id = lt.transaction_id
                 and lleg.amount = sl.leg_amount
```

compares staged **funding-currency** amount (−11 707,31) against ledger **native** amount
(−599 999,64) and never hits. Every cross-currency transfer slips through.

The **funding** side happens to be safe here only because the funding account is the base-currency
side: the funding leg is always in its own account's native currency on both sides
(`staged.funding_amount = fp.amount` vs `lfund.amount`), and `counter_amount` is null on a funding
leg. Same-currency transfers are unaffected (`counter_amount` null, `amount` already native).

## Fix

Use the native amount for the leg when the resolution recorded one:

```sql
coalesce(p.counter_amount, p.amount) as leg_amount
```

Verified against the live DB — with this one change the detection query returns
`(17764, 175)` and the scan raises the match. (An equivalent alternative is to compare against
`coalesce(lleg.base_amount, lleg.amount)` on the ledger side; the `counter_amount` form is closer to
how f2 itself reads the staged leg.)

## Tests

`ImportDuplicateScanSqlLogicTest` needs a crafted cross-currency-transfer case: stage a resolved
cross-currency transfer (`amount` in funding currency, `counter_amount` native), seed a matching
hand-entered ledger transaction (native `posting.amount`, base `posting.base_amount`), rescan,
assert one `pending` match. CLAUDE.md §6 already calls for "the cross-currency ... cases" in the
SQL-logic tier — this path was missed.

## Implementation note (owner-confirmation pending)

`ImportDuplicateScanRepository.MATCH_QUERY` — `staged_leg` now selects
`coalesce(p.counter_amount, p.amount) as leg_amount`, so a resolved cross-currency transfer leg is
compared on its real native far amount against the ledger's native `posting.amount`; a same-currency
leg (`counter_amount` null) is unchanged. Class javadoc updated to state the rule.

`ImportDuplicateScanSqlLogicTest` gains two cases:
`matchesReimportedCrossCurrencyTransferOnTheResolvedNativeFarAmount` (the bug — red before the
one-line change) and `matchesReimportedSameCurrencyTransferThatCarriesNoCounterAmount` (regression
guard for the `coalesce` fallback). New seeding helpers: `transferLeg(..)`, a currency-aware
`account(..)` overload, a `base_amount` `posting(..)` overload.
